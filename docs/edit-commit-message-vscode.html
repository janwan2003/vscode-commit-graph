How to edit a commit message in VS Code (including older commits)

A typo, a missing ticket number, a subject that just says “WIP”: commit messages can be fixed, ideally before anyone else has the commit. The last commit takes one command; an older one takes an interactive rebase. This guide covers both, what rewording does to your history, pushed commits, and how to undo it.

Quick answers

I want to…Run
Replace the message of my last commitgit commit --amend -m "New message"
Change only the message, leaving staged files outgit commit --amend --only
Change an older commit’s messagegit rebase -i <commit>^, then pick → reword
Publish the rewritten branchgit push --force-with-lease
Undo an amendgit reset --soft HEAD@{1}
Undo a reword rebase I just finishedgit reset --keep ORIG_HEAD

The last commit: git commit --amend

Amending replaces the most recent commit with a new one. Give the new message on the command line, or leave out -m to get the old message in your editor:

git commit --amend -m "Fix date parsing in log view"
git commit --amend              # edit the current message in the editor

Watch out for one thing: --amend also adds whatever you have staged to the commit. If you only want to change the message, add --only, which leaves staged changes staged:

git commit --amend --only -m "Fix date parsing in log view"

In VS Code: type the new message in the Source Control message box, then open the … (More Actions) menu at the top of the Source Control view and choose Commit → Commit (Amend). The same command is in the Command Palette as Git: Commit (Amend). Like the terminal command, it includes what is staged, so commit or stash unrelated work first. To have git open messages in a VS Code tab rather than Vim, run git config --global core.editor "code --wait".

An older commit: git rebase -i and reword

For an older commit, an interactive rebase replays the commits from that point on and lets you mark the one to reword. Pass it the parent of the commit you want, which is what the ^ means:

git log --oneline -4
8319fa2 Add export button
415016b Handle empty rows
9738777 fix stuff
385981c Add CSV export
git rebase -i 9738777^

Git opens a todo list, oldest commit first. Change pick to reword (or just r) on the line you want, then save and close:

reword 9738777 # fix stuff
pick 415016b # Handle empty rows
pick 8319fa2 # Add export button

Git then opens the message of that commit. Edit it, save and close, and the rebase replays the rest. You can mark several lines reword at once; git stops for each. If the commit is the very first one in the repository, it has no parent, so use git rebase -i --root instead.

If you have uncommitted changes, add --autostash so git stashes and restores them. To stop halfway, git rebase --abort restores everything. The squash guide shows how to edit the todo list in a VS Code tab.

What changes when you edit a message

A commit’s hash is computed from everything in it, message included, and from its parent’s hash. So changing a message creates a new commit with a new hash, and every commit after it gets a new hash too, because its parent changed. The files and the diffs stay exactly the same. In the example above:

before                        after
8319fa2 Add export button     9842822 Add export button
415016b Handle empty rows     cecdf0c Handle empty rows
9738777 fix stuff             a118b82 Fix date parsing in log view
385981c Add CSV export        385981c Add CSV export

The old commits are not deleted straight away; they are just no longer on your branch. That is why the change can be undone, and also why anything that points at the old hashes (another branch, a tag, a link in an issue) keeps pointing at the old version.

Commits you already pushed

If the commit is already on the remote, your rewritten branch and the remote one have different histories, and a normal git push is rejected. Overwrite the remote branch with the safe form of force-push, which refuses if someone else has pushed to it since you last fetched:

git push --force-with-lease

Do not reword commits on a shared branch such as main. Anyone who already pulled them still has the old hashes, and their next pull will try to merge the two histories. Rewording your own feature branch before a review is normal; on a shared branch, leave the message alone.

Undo it

After an amend, the previous version of the commit is one step back in the reflog (git’s local record of where HEAD has been). A soft reset brings it back without touching your files:

git reset --soft HEAD@{1}

After a rebase, git saves the old branch position in ORIG_HEAD. Go back to it with:

git reset --keep ORIG_HEAD

--keep keeps your uncommitted changes, and refuses to run if one of them is in a file the reset would have to change. Note that ORIG_HEAD is overwritten by the next reset, merge or rebase, and git commit --amend does not set it at all. If it has moved on, find the old position in the reflog: the entry just below rebase (start) is your branch before the rebase.

git reflog
9842822 HEAD@{0}: rebase (finish): returning to refs/heads/main
...
a118b82 HEAD@{3}: rebase (reword): Fix date parsing in log view
...
385981c HEAD@{5}: rebase (start): checkout 9738777^
8319fa2 HEAD@{6}: commit: Add export button
git reset --keep 8319fa2

The undo guide explains the reflog in more detail.

Do it in Mergeline

From Mergeline 0.6 you can reword any commit on your current branch from the graph, without counting commits or editing a todo list.

  1. Right-click the commit and choose Edit commit message…. The item appears only for commits reachable from HEAD, that is, on the branch you have checked out.
  2. Edit the message in the editor that opens over the graph: a subject field and a body field, filled with the current message. Change either or both, then press Save message (or Ctrl/Cmd+Enter); Esc cancels. Since 0.7 the body can be edited too; 0.6 changed only the subject line.
  3. Mergeline rewrites the branch by running a non-interactive git rebase -i with --autostash, so uncommitted changes are stashed and restored for you. If the commit is already on a remote-tracking branch, it warns you first: you will need to force-push afterwards. It refuses if there is a merge commit between the commit and HEAD; use an interactive rebase in a terminal for those.
  4. Changed your mind? The notification that appears when it finishes has an Undo button, which runs git reset --keep to the previous HEAD.
  5. If a later commit conflicts while being replayed, the rebase stops and a bar above the graph shows where, with Continue, Skip, Abort and Source Control buttons (see rebase conflicts).

The same menu has Move commit up / down (see reordering commits), Squash into parent and Drop commit…; see squashing commits and dropping a commit.
