Undo in git: reset, revert, cherry-pick and the reflog

Git almost never forgets a commit. Once something is committed, you can nearly always get it back, even after a reset or a deleted branch. What you choose depends on one question: has the commit been pushed and pulled by anyone else? If not, you can rewrite history with reset. If it has, add a new commit that undoes it with revert. This guide covers both, how to copy commits with cherry-pick, and how to recover from mistakes with the reflog.

git reset: soft, mixed and hard

Git keeps your work in three places: the commit your branch points to (HEAD), the staging area (also called the index: what the next commit will contain), and the working tree (the files on disk). git reset <commit> always moves your current branch to <commit>. The mode decides how many of the other two places are reset to match:

ModeBranch movesStaging areaFiles on diskTypical use
--softYesKeptKeptSquash the last few commits into one: reset, then commit again (other ways to squash).
--mixed (default)YesResetKeptRedo the last commit with different files staged.
--hardYesResetResetDiscard commits and all uncommitted changes to tracked files.
 
# combine the last three commits into one
git reset --soft HEAD~3
git commit -m "Add CSV export"

# make the branch match the remote exactly, dropping local commits
git fetch
git reset --hard origin/main

--hard is the one command here that can lose work for good. Commits it removes can be recovered from the reflog, but uncommitted edits to tracked files are simply overwritten. Untracked files are left alone. If you are not sure, run git stash first, or use git reset --keep <commit>, which refuses to run if it would overwrite your local changes.

Do not reset a branch that others have already pulled. Moving it backwards and pushing requires a force-push, and their copies still have the commits you removed. Use revert instead.

git revert: undo by adding a commit

git revert creates a new commit whose changes are the exact opposite of an earlier one. History is not rewritten, so it is safe on shared branches like main.

git revert 72c5f10               # opens the editor for the message
git revert --no-edit 72c5f10     # uses the default "Revert ..." message
git revert --no-commit HEAD~3..HEAD   # undo the last three, then commit once
git commit -m "Revert the CSV export"

Reverting a merge commit needs -m 1 to say which parent is the mainline (usually the first: the branch you merged into):

git revert -m 1 9f2c1ab

One catch: after reverting a merge, merging the same branch again will not bring those changes back, because git sees them as already merged. To reintroduce the feature, revert the revert commit.

git cherry-pick: copy a commit

git cherry-pick applies the change from an existing commit onto your current branch as a new commit. The classic use is moving a bug fix from main to a release branch without merging everything else.

git switch release/1.4
git cherry-pick -x 4e7d0c2      # -x notes the original hash in the message
git cherry-pick a1b2c3d e4f5a6b  # several commits, applied in the order given
git cherry-pick A^..B            # a range from A to B, including A

Note that A..B excludes A; add ^ to include it. On a conflict, fix the files, git add them and run git cherry-pick --continue, or git cherry-pick --abort to cancel. The copy is a different commit with a different hash, so the same change then exists twice in history; prefer merging when you want all of a branch.

To undo a cherry-pick you just made and have not pushed, git reset --hard HEAD~1 removes it. If it is pushed, revert it.

git reflog: getting lost work back

Every time HEAD moves, by a commit, checkout, reset, rebase or merge, git writes a line to the reflog. It is your local undo history:

git reflog
3a9b6d4 (HEAD -> main) HEAD@{0}: reset: moving to HEAD~2
9f2c1ab HEAD@{1}: commit: Add export button
72c5f10 HEAD@{2}: commit: Fix date parsing in log view
3a9b6d4 (HEAD -> main) HEAD@{3}: checkout: moving from feature to main

Here a hard reset removed two commits. HEAD@{1} is where the branch was just before it, so either of these brings them back:

git reset --hard HEAD@{1}       # move the branch back
git branch rescue 9f2c1ab       # or keep them on a new branch

The same works after a rebase that went wrong: find the rebase (start) entry, take the entry directly below it (the position just before the rebase began), and reset to that. git reflog show feature lists only the moves of the feature branch, which is often easier to read.

Deleted a branch? git branch -D prints the hash it pointed at, for example Deleted branch feature (was 4e7d0c2). Recreate it with git branch feature 4e7d0c2. If that message is gone, search the reflog for checkout: moving from feature.

Limits worth knowing: the reflog is local to your clone and is not pushed. By default git keeps entries for 90 days, and 30 days for commits no longer reachable from any branch, before garbage collection may remove them. And it only records commits, so uncommitted edits lost to reset --hard are not in it. (Changes that were staged may still be found with git fsck --lost-found, which writes unreferenced file contents into .git/lost-found/, but do not rely on it.)

Do it in Mergeline

The graph shows exactly which commit you are about to move to, which takes most of the guesswork out of HEAD~3-style arithmetic.

  1. Reset: right-click the commit you want your current branch to point at, choose reset, and pick soft, mixed or hard. A hard reset asks for confirmation in a modal dialog. The uncommitted-changes row at the top shows what a soft or mixed reset left behind.
  2. Revert: right-click a commit and choose revert. The new revert commit appears at the top of your branch.
  3. Cherry-pick: check out the target branch, then right-click the commit on another lane and choose cherry-pick. Use find to locate it by subject, author or hash.
  4. Reflog recovery: Mergeline draws branches, tags and stashes, not the reflog, so commits that nothing points to are not in the graph. Find the hash with git reflog in the terminal, run git branch rescue <hash>, then click Refresh. The rescued commits appear with a rescue badge, ready to merge, cherry-pick or reset to.
