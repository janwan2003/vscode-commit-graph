A git graph in Cursor, VSCodium and other VS Code forks

Cursor, VSCodium, Windsurf and Gitpod all look like VS Code, and most VS Code extensions run in them unchanged. Where they differ is the shop. When you search the Extensions view in one of these editors, you are not searching Microsoft’s Visual Studio Marketplace but a different registry, usually Open VSX. That explains why an extension you know from VS Code is sometimes missing, sometimes listed by a different publisher, and sometimes several versions behind. This guide explains how that works, how to install an extension that is not listed at all, and what to check before you settle on a git graph extension in a fork.

Why forks install extensions from Open VSX

The Visual Studio Marketplace is Microsoft’s service, and its terms of use limit what it may be used with. They list Visual Studio, Visual Studio Code, GitHub Codespaces, Azure DevOps and their successors as the “In-Scope Products and Services”, and say that Marketplace offerings may be installed and used only with those products. An editor built from VS Code’s open-source code is not on that list, so a fork that wants a built-in extension store needs a different one.

Open VSX fills that role. It is a vendor-neutral, open-source extension registry run under the Eclipse Foundation, and it speaks the same protocol as Microsoft’s gallery, so an editor only has to point at a different URL. Here is what the editors themselves document:

  • VSCodium sets Open VSX as its extension gallery in its product.json, and its documentation cites Microsoft’s terms as the reason.
  • Cursor uses Open VSX for third-party extensions, routed through its own marketplace proxy that scans extensions before offering them. For a few popular extensions that are not on Open VSX it publishes its own replacement builds.
  • Windsurf downloads extensions from an Open VSX mirror by default, and lets you change the marketplace URLs in its settings.
  • Gitpod (now Ona) built OpenVSCode Server, the browser version of VS Code it ships, with Open VSX as the configured gallery.

Sources, read 20 November 2026: the Visual Studio Marketplace Terms of Use; VSCodium’s docs/extensions.md; Cursor’s help page on extensions; Windsurf’s advanced configuration and recommended-extensions pages; the product.json in the gitpod-io/openvscode-server repository.

What this means in practice: an extension shows up in a fork’s Extensions view only if its author, or someone else, has published it to Open VSX. Publishing there is a separate step from publishing to Microsoft’s Marketplace, with a separate account, and not every author does it. Cursor’s own documentation points out a second consequence: the same publisher.name ID can belong to a different publisher, or different code, on Open VSX than on the Marketplace. Treat an extension ID the way you would treat a package dependency, and check who published it.

Installing a .vsix in each editor

Every extension is distributed as a single .vsix file, which is a zip archive with a manifest. Registries are a convenient way to find and update those files, but you can always install one directly. Many authors attach the .vsix to each GitHub release for exactly this reason. All of these editors share VS Code’s extension machinery, so the steps are nearly identical.

From the Command Palette (any editor)

  1. Download the .vsix file.
  2. Open the Command Palette with Ctrl+Shift+P (Cmd+Shift+P on macOS).
  3. Run Extensions: Install from VSIX… and pick the file. The same entry is in the … menu at the top of the Extensions view.

In VSCodium, Cursor and Windsurf this is the whole process. In a browser-based editor such as Gitpod, the editor runs on a remote machine, so first put the file into the workspace (drag it into the Explorer, or download it there from a terminal with curl -LO), then run the same command and choose it.

From a terminal

Each editor’s command-line launcher accepts the same flag, if you have it on your PATH:

code --install-extension mergeline-0.5.0.vsix     # VS Code
codium --install-extension mergeline-0.5.0.vsix   # VSCodium
cursor --install-extension mergeline-0.5.0.vsix   # Cursor

This is handy in a setup script or a dev container, where you want the same extensions every time without clicking.

One thing to keep in mind: an extension installed from a file stays at that version until you install a newer file. If the extension is later listed in your editor’s registry, install it from the Extensions view instead, and updates will arrive like any other extension’s.

What to look for in a git graph extension on Open VSX

A git graph is something you open many times a day and trust with operations such as reset and rebase, so it is worth a few minutes of checking. These questions apply to any extension in a fork:

  • Is it maintained? Open the listing on open-vsx.org and look at the version and its date, then at the project’s release history. Compare the Open VSX version with the extension’s own latest release: a listing can lag behind the Marketplace if the author publishes there by hand. Sometimes an old date simply reflects the project’s history. The Git Graph listing on Open VSX, for example, is version 1.30.0 from 2021 (Open VSX API, read 20 November 2026), which matches that extension’s latest release anywhere.
  • Who published it? Check that the Open VSX publisher is the same person or organisation as the source repository, and that the listing links back to it. Open VSX marks publishers who have verified ownership of their namespace.
  • Does it work without telemetry? Many people choose VSCodium precisely because it ships with telemetry off. An extension can still send data of its own, so read its privacy notes or source, and prefer one that sends nothing or clearly follows the editor’s telemetry setting.
  • Does it need anything Microsoft-only? Some extensions depend on other extensions that exist only on the Marketplace, or on menus and APIs that behave differently in forks. A graph that draws its own right-click menus and uses only standard extension APIs is less likely to break.
  • Can it be forked? If the licence allows forks to be published, someone can keep the extension going if its author stops. The Git Graph alternative guide explains why that matters.
  • Does it handle your setup? Remote windows, multi-root workspaces, worktrees and large repositories all trip up some tools. Try it on your biggest repository before relying on it.

Whichever extension you pick, the terminal graph is always there as a fallback. The git log --graph reference covers the flags that make it readable.

Use Mergeline in Cursor, VSCodium or Windsurf

Mergeline is a free, MIT-licensed git graph built for VS Code and the editors built on it. It uses only standard VS Code extension APIs (no proposed APIs), draws its own right-click menus, needs VS Code 1.85 or an editor built on it, and sends no telemetry. Its end-to-end test suite passes in VS Code 1.147 and VSCodium 1.143; Cursor and Windsurf have not been tested yet. If something behaves differently in your editor, please open an issue.

  1. Install it. Once Mergeline is listed on Open VSX and the VS Code Marketplace, search for Mergeline in the Extensions view. Until then, download the .vsix from the latest GitHub release and install it with Extensions: Install from VSIX… or one of the commands above.
  2. Open a git repository and trust it. Mergeline runs git commands, so it is disabled in Restricted Mode. Git must be on your PATH, on the remote machine if you work in a remote window.
  3. Open the graph with the Mergeline button in the Source Control title bar, the Graph button in the status bar, or Mergeline: Show Commit Graph from the Command Palette.
  4. Work from the graph. Every branch, tag and stash appears in coloured lanes. Click a commit for its details and per-file diffs, right-click it to check out, merge, rebase, cherry-pick, revert or reset, and right-click any file and choose Show File History in Mergeline to see only the commits that touched it (file history guide).

FAQ

Is Mergeline on Open VSX yet?

Not yet. The Open VSX and VS Code Marketplace listings are being set up. Until they are live, the .vsix on GitHub releases is the way to install it. Once a listing is live, install from the Extensions view so you get updates.

Can I point VSCodium or Cursor at Microsoft’s Marketplace instead?

The registry URL is a setting in these editors, and some people change it. Microsoft’s terms, though, limit Marketplace offerings to Microsoft’s own products, so that is a question for you and those terms. Installing an extension’s .vsix from its own release page avoids it entirely.

Do I need the built-in Git extension?

Mergeline runs git itself to draw the graph. For push, pull and fetch it goes through the editor’s built-in Git extension when that is available, so your usual credential prompts work. Editors built on VS Code normally ship that extension, since it is part of VS Code’s open-source code.

Where do I start if I just want a quick look at the branches?

Run git log --graph --oneline --all in the integrated terminal, or read three ways to see a branch graph in VS Code.
