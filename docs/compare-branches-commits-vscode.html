Compare two branches or commits in VS Code

Before you merge a branch, review someone’s work locally, or hunt for what broke between two releases, you need the same thing: the difference between two points in history. Git can answer two different questions here, which files differ and which commits differ, and the commands for them look alike but do not behave alike. This guide covers the git commands, what VS Code’s built-in graph offers, and how to compare any two commits in Mergeline.

Two dots or three: what are you comparing?

Take a branch feature made from main at commit A. On the branch, B edits src/app.ts and C adds src/export.ts. Meanwhile D landed on main and edited README.md:

          B---C  feature
         /
    A---D  main

Two dots, or a space, compare the two snapshots directly. git diff main feature and git diff main..feature are the same command:

git diff --name-status main feature
M       README.md
M       src/app.ts
A       src/export.ts

README.md is listed although nobody touched it on feature. From feature’s point of view, the line D added is missing, so the diff shows it being removed. On a branch that has been open for a while, this noise from main can drown out the branch’s own work.

Three dots compare against the merge base, the last commit both branches share (A here). git diff main...feature shows only what feature did since it split off:

git diff --name-status main...feature
M       src/app.ts
A       src/export.ts

It is shorthand for git diff $(git merge-base main feature) feature; recent versions of git also accept git diff --merge-base main feature. This is the comparison a pull request’s “Files changed” view shows on GitHub. Order matters: git diff feature...main shows what main gained instead.

Branch names are just commits, so all of this works with hashes, tags and remote branches. Run git fetch first, then compare against origin/main; a stale remote-tracking branch gives a confidently wrong answer.

Just the list of files

git diff --stat main...feature
 src/app.ts    | 1 +
 src/export.ts | 1 +
 2 files changed, 2 insertions(+)
git diff --name-only main...feature          # paths only, handy for scripts
git diff --name-status main...feature        # A added, M modified, D deleted, R renamed
git diff --diff-filter=D --name-only main...feature   # only deleted files

Git detects renames by default, so a moved file shows as one R line with both paths rather than a delete plus an add.

Which commits differ: git log

Here the dots mean something else, which trips up almost everyone. For git log, main..feature means “commits reachable from feature but not from main”: exactly what a merge would bring in.

git log --oneline main..feature
c31fb08 Add CSV export
0ce59e1 Retry failed requests
git log --oneline feature..main                     # what feature is missing from main
git log --oneline --left-right main...feature        # both sides, marked < and >
< 5f8a5f9 Update README
> c31fb08 Add CSV export
> 0ce59e1 Retry failed requests
git rev-list --left-right --count main...feature
1       2

The last command is the “ahead and behind” count: main has 1 commit that feature lacks, and feature has 2. Add --cherry-pick to the --left-right log to hide commits that were cherry-picked across and exist on both sides. After a git fetch, git log --oneline HEAD..@{upstream} lists what a pull would bring down.

One file across branches

git diff main feature -- src/app.ts        # the file as it is on each branch
git diff main...feature -- src/app.ts     # only feature's changes to it
git diff main:src/app.ts feature:src/core/app.ts   # the file was moved on one side
git show feature:src/app.ts                  # print the whole file from a branch

In the branch:path form the path starts at the top of the repository. To read these diffs in VS Code’s side-by-side editor instead of the terminal, register it as git’s diff tool once:

git config --global diff.tool vscode
git config --global difftool.vscode.cmd 'code --wait --diff $LOCAL $REMOTE'
git difftool main...feature -- src/app.ts

Keep the single quotes so your shell does not expand $LOCAL and $REMOTE. Without a path, git difftool opens each changed file in turn and asks before each one. In VSCodium use codium, in Cursor cursor.

Against your working tree

git diff                # edits not yet staged
git diff --staged       # what the next commit will contain
git diff HEAD           # everything uncommitted, staged or not
git diff main            # your files on disk compared with main

Untracked files never appear in git diff. Run git add -N <file> (“intent to add”) to make a new file show up without staging its content.

VS Code’s built-in compare

Recent versions of VS Code can compare from the Source Control Graph in the Source Control view. In VS Code 1.147, right-clicking a commit offers three actions: Compare with Remote (your branch’s upstream), Compare with Merge Base (the branch VS Code considers your current branch’s base; greyed out when it cannot tell) and Compare with…, which asks you to pick a branch, remote branch or tag. The result opens in a multi-file diff editor with every changed file stacked in one tab.

Two details are worth knowing. All three use three-dot semantics: VS Code runs git diff <picked>...<commit>, so you see what the clicked commit added since the two sides split, not a direct comparison of two snapshots. And Compare with… lists branches and tags only, so comparing two arbitrary commits still means the terminal. (We read the menu entries and the command they run from the git extension bundled with VS Code 1.147; older versions may not have them.) For a single file, the Timeline view compares each version with the one before it.

Do it in Mergeline

In the graph you can see both sides of the comparison before you make it, including where the branches split.

  1. Select the first commit. Click it. To compare branches, click the commit carrying the branch’s badge, which is its tip.
  2. Add the second. Ctrl-click (Cmd-click on macOS) another commit. The details pane switches to Comparing <older> → <newer> and lists every file that differs, with lines added and removed and renames shown. The lower row in the graph is always the “from” side, so the click order does not matter.
  3. Open a file. Click it to open the change in VS Code’s own diff editor.
  4. Choose the right base. This is a direct comparison, the same as git diff A B. For the three-dot view of what a branch changed, Ctrl-click the commit where its lane leaves main instead of the tip of main.
  5. Compare with your working tree. When you have uncommitted changes, a row at the top of the graph holds them. Select it, then Ctrl-click any commit to compare that commit with the files on disk, untracked files included. Mergeline 0.4.0 also adds Compare with working tree to a commit’s right-click menu, and a compare-with-current-branch item to a branch badge’s menu, which compares that branch’s tip with yours in one click.
  6. Only what the branch changed (three dots). Since 0.5.0 a branch’s menu also has Changes since it split from your current branch. That is git diff current...branch: the files changed on the branch since the merge base, which the details pane names. You can also drag one branch badge onto another and pick Compare or Changes on … since it split from … from the menu that opens.

Click any commit without Ctrl to go back to its normal details, or press Esc to close the pane.

FAQ

Why does my diff show changes I never made?

You are almost certainly using two dots (or a space) against a branch that has moved on. The diff is reporting the other branch’s new work as if you had removed it. Use three dots, git diff main...feature, to see only your side.

How do I compare my branch with a fork or another remote?

Add it as a remote and fetch it, then compare as usual: git remote add upstream <url>, git fetch upstream, git diff upstream/main...HEAD. Fetched branches also appear in Mergeline’s graph, ready to Ctrl-click.

Does it work in VSCodium, Cursor and Windsurf?

It is built for them (they install the same .vsix, and Mergeline uses only standard VS Code APIs); our automated tests run in VS Code 1.147 and VSCodium 1.143. Download it from the latest GitHub release and run Extensions: Install from VSIX… (full steps). Listings on the VS Code Marketplace and Open VSX are coming soon.
