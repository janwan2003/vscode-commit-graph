git log --graph: the command, its flags, and how to read it

Git can draw your branch history as text, right in the terminal, with no tools beyond git itself. The command most people want is:

git log --graph --oneline --all

This page explains what each part of that does, the flags that change which commits appear and in what order, how to save your favourite combination as an alias, and how to read the characters in the output. Every example below was produced by running the command on a small test repository with two branches, a merge, an unmerged fix branch and two tags. The output is pasted as git printed it, apart from colours and trailing spaces.

The basic command

git log --graph --oneline --decorate --all
* 69ba820 (HEAD -> main, tag: v0.2.0) Bump version to 0.2.0
| * f43a99f (fix/typo) Fix typo in README
|/
*   f767072 Merge branch 'feature/search'
|\
| * 1e5371a (feature/search) Highlight matches
| * bd15499 Add search box
* | 962fa80 Fix config defaults
|/
* dbe5f6d (tag: v0.1.0) Add config loader
* b68fa30 Initial commit
  • --graph draws the lines to the left of each commit. It also turns on parent rewriting: when some commits are hidden (by a path or another filter), the ones that remain are drawn as if connected directly, so the graph does not fall apart.
  • --oneline prints one line per commit: the abbreviated hash and the subject. It is shorthand for --pretty=oneline --abbrev-commit.
  • --all starts from every ref under refs/ plus HEAD: local branches, remote-tracking branches, tags, and the latest stash, which shows up as a small merge-shaped commit labelled refs/stash. Without it you see only the history of the branch you are on, which is why fix/typo would be missing from the example.
  • --decorate prints the branch and tag names in brackets. Git’s default for log.decorate is auto, which shows them only when the output goes to a terminal. If you pipe the output to a file, less or another command, the names disappear unless you pass --decorate yourself.

Long output opens in a pager. Press q to leave it, or limit the number of commits with -n 30.

Reading the ASCII graph

Read it from the top: the newest commits come first, and every commit appears below all of its children.

  • * is a commit. The column it sits in is the line of history it belongs to in this drawing.
  • | is a line of history passing by. On the row * | 962fa80, the commit is in the left column while the right-hand line (the feature branch) continues past it.
  • \ under a commit marks a merge. *   f767072 followed by |\ means that commit has two parents. The straight line down on the left leads to its first parent (962fa80, the branch that was checked out during the merge); the \ leads to its second parent (1e5371a, the branch merged in). Extra spaces after the * leave room for that fork.
  • / marks where a branch started. Reading upwards, |/ above dbe5f6d means the right-hand line splits off from that commit. Both the feature branch and main’s own commit 962fa80 have dbe5f6d as their parent.

The example also shows that a branch name is only a label. feature/search still points at 1e5371a even though main already contains it, while fix/typo sits on a line that never rejoins: that work has not been merged.

Choosing which commits to show

Instead of --all, you can name the starting points: --branches for local branches, --remotes for remote-tracking branches, --tags for tags, or any mix of branch names. A range such as main..fix/typo shows the commits reachable from fix/typo but not from main; on the test repository it prints just f43a99f, which is what a merge of fix/typo would bring in.

--first-parent

git log --graph --oneline --decorate --first-parent
* 69ba820 (HEAD -> main, tag: v0.2.0) Bump version to 0.2.0
* f767072 Merge branch 'feature/search'
* 962fa80 Fix config defaults
* dbe5f6d (tag: v0.1.0) Add config loader
* b68fa30 Initial commit

At each merge, git follows only the first parent, so the commits that came in from the feature branch drop out. On a main branch where every change arrives through a merged pull request, this gives one line per merge, which is a compact changelog.

--simplify-by-decoration

git log --graph --oneline --decorate --all --simplify-by-decoration
* 69ba820 (HEAD -> main, tag: v0.2.0) Bump version to 0.2.0
| * f43a99f (fix/typo) Fix typo in README
|/
* 1e5371a (feature/search) Highlight matches
* dbe5f6d (tag: v0.1.0) Add config loader
* b68fa30 Initial commit

Only commits that a branch or tag points to are kept, plus a few that git adds so the history still makes sense (here, the root commit). On a big repository this shrinks the graph to a map of where branches and releases are. Notice the trade-off: the merge commit is gone, so 1e5371a appears directly below the tip of main, and the graph no longer shows that a merge happened at all.

One path: -- <path>

Put a file or directory after -- to keep only commits that changed it. On the test repository, git log --graph --oneline --all -- src/config.js prints three commits in a straight line: the merge is left out because its copy of the file is identical to the copy in one of its parents, so the merge itself did not change it. The file history guide covers this in depth, including --follow for renamed files.

Commit order: --date-order and --topo-order

Git never prints a commit before its children. Within that rule, there are several orders. According to git’s documentation, --graph uses --topo-order unless told otherwise: commits from one line of history stay together, as in the first example, where both feature-branch commits appear before 962fa80. With --date-order, commits are sorted by commit timestamp instead:

git log --graph --oneline --all --date-order
* 69ba820 Bump version to 0.2.0
| * f43a99f Fix typo in README
|/
*   f767072 Merge branch 'feature/search'
|\
| * 1e5371a Highlight matches
* | 962fa80 Fix config defaults
| * bd15499 Add search box
|/
* dbe5f6d Add config loader
* b68fa30 Initial commit

Here 962fa80 (4 November) sits between the two feature commits (3 and 5 November), which is when it actually happened. Date order is better for “what was going on that week”; topological order is better for “what did this branch contain”, and on a busy repository it produces far fewer crossing lines. --author-date-order sorts by author date, which differs from commit date after a rebase or cherry-pick: rebasing rewrites the commit date but keeps the original author date.

A custom format and a git lg alias

--oneline leaves out who made a commit and when. A format string adds them. Save it as an alias so you never type it again:

git config --global alias.lg "log --graph --all --date=short --format='%C(auto)%h%d %s %C(dim)%an, %ad'"
git lg
* 69ba820 (HEAD -> main, tag: v0.2.0) Bump version to 0.2.0 Ana Dev, 2026-11-08
| * f43a99f (fix/typo) Fix typo in README Ana Dev, 2026-11-07
|/
*   f767072 Merge branch 'feature/search' Ana Dev, 2026-11-06
|\
| * 1e5371a (feature/search) Highlight matches Ana Dev, 2026-11-05
| * bd15499 Add search box Ana Dev, 2026-11-03
* | 962fa80 Fix config defaults Ana Dev, 2026-11-04
|/
* dbe5f6d (tag: v0.1.0) Add config loader Ana Dev, 2026-11-02
* b68fa30 Initial commit Ana Dev, 2026-11-01

The placeholders: %h is the short hash, %d the branch and tag names, %s the subject, %an the author name and %ad the author date in the style set by --date. %C(auto) colours the hash and names the way git normally would, and %C(dim) greys out the rest of the line. Swap %ad for %ar to get “3 days ago” instead of a date. Anything you type after the alias is added to the command, so git lg -n 20, git lg --first-parent and git lg -- src/ all work.

When the terminal graph gets hard to read

On a small repository the text graph is perfect. It is exact, it works over SSH, and you can pipe it into other commands. It gets harder as the history grows:

  • Width. Every branch that is open at the same time needs its own column. With a dozen active branches the graph pushes the commit subjects off the right edge of the screen, and lines that cross each other are drawn with / and \ characters that are easy to mistrack.
  • Length. A few hundred commits fill many screens. Finding where a branch started means scrolling and matching columns by eye.
  • Nothing to click. To see what a commit changed you copy its hash into git show; to act on it you copy the hash again into git merge, git rebase or git reset.
  • Stale remotes. Remote-tracking branches only move when you fetch, so run git fetch --all --prune first or the graph shows an old picture.

The flags above help a lot with the first two. For the rest, a graphical view earns its place. The branch graph guide compares the terminal, VS Code’s built-in Source Control Graph and a graph extension side by side.

The same graph in VS Code, with Mergeline

Mergeline is a free, MIT-licensed extension that draws this graph inside VS Code (and editors built on it, such as VSCodium and Cursor) and keeps the git options you just learned within reach:

  • Order menu. The toolbar’s Order menu has Date, Topology and Author date. Mergeline passes --date-order, --topo-order or --author-date-order to git, so they behave exactly as described above. The mergeline.commitOrder setting sets the default.
  • All refs, or one branch. By default the graph starts from all branches, tags and remote-tracking branches (Mergeline passes --branches --tags --remotes, close to --all), plus stashes and a row for uncommitted changes. The branch filter shows a single branch, and the Remotes toggle hides remote-tracking branches, the graphical version of dropping --remotes.
  • File history. Right-click a file and choose Show File History in Mergeline for the equivalent of git log --graph -- <path>: only the commits that touched the file, still connected through rewritten parents, and followed back through renames.
  • Columns and details. Author, date and hash get their own columns, so there is no format string to remember. Click a commit for its full message and changed files, and open any file in the diff editor.
  • Actions. Right-click a commit or branch to check out, merge, rebase, cherry-pick, revert or reset, with a confirmation before each one.

To install, search for Mergeline in the Extensions view once it is listed on the VS Code Marketplace and Open VSX. Until then, download the .vsix from the latest GitHub release and run Extensions: Install from VSIX…, or code --install-extension mergeline-0.2.0.vsix (full steps; for Cursor and VSCodium see installing in VS Code forks). Then open the graph with Mergeline: Show Commit Graph.
