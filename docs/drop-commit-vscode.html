How to delete (drop) a commit in VS Code

Sometimes a commit should simply not be there: debug logging you committed by accident, an experiment that went nowhere, a change that belongs on another branch. Git can remove it from your branch and replay the commits that came after it. Whether you should depends on one question: has anyone else got this commit yet? This guide covers dropping a commit, the safer alternative for shared history, what to do when the removal conflicts, and how to get the commit back.

Drop or revert?

Dropping rewrites history: the commit disappears from the branch and every later commit is recreated with a new hash. That is fine on a branch only you use. Reverting leaves history alone and adds a new commit that does the opposite of the old one:

git revert 72c5f10

Use revert for anything already pushed to a shared branch such as main. If you drop a commit there and force-push, everyone who pulled it still has it, and it will come back the next time they merge. The undo guide covers revert in detail, including reverting merges.

Drop any commit with git rebase -i

An interactive rebase replays your commits from a starting point and lets you decide what happens to each. Start from the parent of the commit you want to remove (that is what ^ means):

git log --oneline -4
f16153e Add export button
44ee6f8 Handle empty rows
848a197 Add debug logging
0993a57 Add CSV export
git rebase -i 848a197^

In the todo list that opens (oldest commit first), change pick to drop on the commit to remove, or delete its line. Save and close:

drop 848a197 # Add debug logging
pick 44ee6f8 # Handle empty rows
pick f16153e # Add export button

Git rebuilds the branch without that commit. To skip the editor, git rebase --onto 848a197^ 848a197 does the same thing in one line: it takes everything after 848a197 and replays it onto that commit’s parent. If the commit is the first one in the repository, use git rebase -i --root.

Rebase will not start with uncommitted changes; add --autostash to stash and restore them automatically. To edit the todo list in a VS Code tab, see the squash guide.

Drop the latest commits with git reset

If the commits to remove are the newest ones on the branch, nothing needs replaying. Move the branch back instead:

git reset --keep HEAD~1    # remove the last commit and its changes
git reset --keep HEAD~3    # remove the last three
git reset --soft HEAD~1    # remove the commit, keep its changes staged

--keep throws away the commits’ changes but keeps your uncommitted edits, and refuses if it would have to overwrite one of them. --hard does the same without that check, so it can silently discard uncommitted work. --soft is “uncommit” rather than delete: the changes stay, ready to commit again differently. The undo guide compares the modes.

When later commits depend on the dropped one

Dropping a commit means replaying the later ones without it. If a later commit edits lines that the dropped commit added, git cannot apply it cleanly and stops:

CONFLICT (content): Merge conflict in src/export.ts
error: could not apply 44ee6f8... Handle empty rows

You have three ways out:

  • Resolve it. Open the conflicted files (VS Code lists them under Merge Changes in Source Control), decide what the code should be now that the dropped commit is gone, then git add the files and run git rebase --continue.
  • Skip that commit too with git rebase --skip. This drops the conflicting commit as well, so only use it if you meant to.
  • Give up with git rebase --abort. The branch goes back exactly as it was before you started, dropped commit included.

A conflict like this is often a sign that the commit is not really independent. Reverting it instead, as a new commit at the top of the branch, may be simpler.

Get a dropped commit back

Dropping a commit does not delete it straight away; it is just no longer on any branch. Right after a rebase or reset, git keeps the old position in ORIG_HEAD:

git reset --keep ORIG_HEAD

ORIG_HEAD is overwritten by the next reset, rebase or merge. After that, look in the reflog, git’s local record of where HEAD has been. The entry just below rebase (start) is your branch before the rebase:

git reflog
9a7766e HEAD@{0}: rebase (finish): returning to refs/heads/main
...
0993a57 HEAD@{3}: rebase (start): checkout 848a197^
f16153e HEAD@{4}: commit: Add export button
git reset --keep f16153e        # put the whole branch back
git cherry-pick 848a197         # or just re-apply the dropped commit

The reflog is local to your clone and entries expire (by default after 30 days for commits no branch points to), so do not leave it too long. The undo guide has more on the reflog.

Do it in Mergeline

From Mergeline 0.6 you can drop a commit on your current branch straight from the graph.

  1. Right-click the commit and choose Drop commit…. The item appears only for commits reachable from HEAD, that is, on the branch you have checked out. The commit is removed and the later commits are replayed on top of its parent.
  2. Mergeline checks first. It runs a non-interactive git rebase -i with --autostash, so uncommitted changes are stashed and restored. It warns you if the commit is already on a remote-tracking branch, because you will need to force-push (and on a shared branch, revert is usually the better choice). It refuses if there is a merge commit between the commit and HEAD; use an interactive rebase in a terminal for those.
  3. Undo in one click. When it finishes, the notification offers Undo, which runs git reset --keep to the previous HEAD.
  4. If a later commit conflicts, the rebase stops and the notification offers Open Source Control, where you resolve the conflict (then git rebase --continue finishes the job), or Abort rebase, which runs git rebase --abort.
  5. Want revert instead? Right-click the commit and choose Revert; it works on any commit, pushed or not.

The same menu has Edit commit message… and Squash into parent; see editing a commit message and squashing commits.
