Git worktrees in VS Code: work on two branches at once

A git worktree is a second (or third) working folder attached to the same repository, with a different branch checked out in each. You can leave a half-finished feature exactly as it is, open another branch in a folder next to it, and switch between them by switching windows. This guide covers the git worktree commands, how to open each worktree in VS Code, Cursor or VSCodium, and the errors you are likely to see.

What a worktree is, and when to use one

Every repository has one main worktree: the folder that contains .git. git worktree add creates linked worktrees: extra folders, each with its own checked-out files, its own staging area and its own HEAD, all backed by the same repository. A commit made in one is immediately visible in the others, because there is only one set of branches.

Typical uses:

  • Review a pull request while mid-feature. Check the PR branch out in a sibling folder, run it, then close the window. Your feature branch never moves.
  • Run a long test suite or build on another branch while you keep editing this one.
  • Ship a hotfix without stashing. Create a worktree for main or a release branch, fix, commit, push, remove it.

Compared with git stash, a worktree leaves your current changes alone: nothing is put away, so nothing has to be restored. Compared with a second git clone, a worktree shares the object store, so it does not download or store history twice. It also shares branches, tags, remote-tracking branches, stashes and the repository config. A branch created or fetched in one folder exists in all of them.

One rule follows from sharing branches: a branch can be checked out in only one worktree at a time. If two folders had the same branch checked out, a commit in one would silently move the branch under the other. Git refuses instead (see Common errors). A detached HEAD, a checkout of a commit rather than a branch, has no such limit.

Create a worktree: git worktree add

The form is git worktree add <path> [<branch or commit>]. The common cases:

git worktree add ../repo-hotfix hotfix                           # existing local branch
Preparing worktree (checking out 'hotfix')
HEAD is now at 98c7cf6 Fix rounding in totals
git worktree add -b new-branch ../repo-new main                  # new branch, starting at main
git worktree add --detach ../repo-check 1a2b3c4                  # a commit, no branch
git worktree add --track -b feature ../repo-feature origin/feature # a remote branch
  • New branch: -b creates the branch at the commit you name (or at HEAD) and checks it out in the new folder.
  • Detached: for building or testing an old release or tag without creating a branch.
  • Remote branch: run git fetch first. --track -b feature <dir> origin/feature makes a local feature that tracks origin/feature, so git pull and git push work in the new folder without arguments. If no local feature exists yet and exactly one remote has that branch, git worktree add ../repo-feature feature does the same thing for you.

Put worktrees next to the repository, not inside it, where they would show up as untracked files. A common convention is sibling folders named after the repository and the branch, such as shop, shop-hotfix and shop-review, so they sort together.

List and inspect worktrees

git worktree list
/home/me/shop          4f8121c [main]
/home/me/shop-check    1a2b3c4 (detached HEAD)
/home/me/shop-hotfix   98c7cf6 [hotfix]
/home/me/shop-review   d41e7a0 [feature] locked
/home/me/shop-old      0c5b2e9 [spike] prunable

Each line is a folder, the commit it has checked out and its branch. The first line is always the main worktree. Annotations:

Shown asMeaning
(detached HEAD)The worktree has a commit checked out, not a branch. Commits made there belong to no branch until you create one.
lockedSomeone ran git worktree lock on it, so prune, move and remove leave it alone.
prunableIts folder is gone. Git still remembers it (and still treats its branch as checked out) until you run git worktree prune.

For scripts, git worktree list --porcelain prints one attribute per line (worktree, HEAD, branch refs/heads/… or detached, plus locked or prunable with a reason), with a blank line between worktrees. Add -z to separate with NUL characters for paths that contain newlines.

Open a worktree in VS Code, Cursor or VSCodium

A worktree is an ordinary folder, so you open it like any other project:

  • File > Open Folder… and pick the worktree folder, or File > New Window first to keep the current one open.
  • From a terminal: code ../repo-hotfix opens it in a new window. Use cursor in Cursor and codium in VSCodium. -n forces a new window and -r reuses the current one.

Each window has its own Source Control view, showing that folder’s branch, staged files and changes. Commit and push from the window of the worktree you are working in. If you prefer one window, add the worktree with File > Add Folder to Workspace… (or code -a ../repo-hotfix): you get a multi-root workspace, and Source Control lists each folder as a separate repository. Recent versions of VS Code also list a repository’s worktrees in the Source Control Repositories view.

Things that do not carry over: anything ignored by git. Each worktree needs its own node_modules, virtual environment, build output and untracked .env file, so expect to run your install step once in a new folder.

Remove, prune, lock and move

git worktree remove ../repo-hotfix           # deletes the folder; the branch and its commits stay
git worktree remove --force ../repo-hotfix   # also when it has uncommitted changes (they are lost)
git worktree prune                          # forget worktrees whose folder was deleted by hand
git worktree lock --reason "on USB drive" ../repo-usb
git worktree unlock ../repo-usb
git worktree move ../repo-hotfix ../shop-hotfix
  • remove only works on a clean worktree. --force deletes modified and untracked files with the folder, and there is no undo for changes that were never committed. The main worktree cannot be removed.
  • prune is for folders you deleted by hand. Until you prune, their branch still counts as checked out. git worktree prune -n -v shows what it would remove. git gc also prunes stale records on its own after a while.
  • lock is for worktrees on a removable drive or network share that is not always mounted: it stops prune from discarding them while the drive is away.
  • move relocates a linked worktree and updates git’s records. Moving the folder by hand breaks the link; git worktree repair fixes it.

Worktrees in Mergeline

Since 0.5.0, Mergeline shows the repository’s other worktrees in the graph and lets you create, open and remove them from the right-click menu. (Install Mergeline if you do not have it yet.)

  1. See them: every other worktree appears as a badge, ⧉ followed by its folder name, on the commit it has checked out. Hover it for the full path and branch. A worktree whose folder is gone shows a dashed, struck-through badge.
  2. Create one for a branch: right-click a local or remote branch badge and choose Check out in new worktree…. Mergeline asks for the folder, suggesting a sibling such as shop-hotfix. A remote branch becomes a local branch that tracks it (git worktree add --track -b), or uses the existing local branch of that name.
  3. Create one for a commit: right-click any commit and choose Create worktree here (detached)…, which runs git worktree add --detach. When it finishes, a notification offers to open the new folder in a new window.
  4. Use the badge: right-click a worktree badge for Open in new window, Copy path and Remove worktree…. Remove asks first; if the worktree has uncommitted changes, it asks again before running git worktree remove --force. On a badge whose folder is gone, choose Prune missing worktrees.
  5. Branches already in a worktree: a branch that another worktree has checked out offers Open its worktree in new window in place of Check out, so you go to where it is instead of hitting the “already used by worktree” error.

Common errors

fatal: 'hotfix' is already used by worktree at '/home/me/shop-hotfix' (older git versions say is already checked out at). You tried to check out, with git worktree add, git switch or git checkout, a branch that another worktree has checked out. Fixes: work in that worktree instead (git worktree list shows where it is); switch that worktree to another branch; remove it if you are done with it; or, if the folder no longer exists, run git worktree prune. To only look at the code, git worktree add --detach <dir> hotfix checks out the same commit without the branch.

fatal: '../repo-usb' is a missing but locked worktree. Git still has a locked record for that path, and its folder is not there. If the drive is simply unplugged, plug it in. If the worktree is really gone, run git worktree unlock ../repo-usb and then git worktree prune. The unlocked variant, is a missing but already registered worktree, needs only the prune.

fatal: '../repo-hotfix' contains modified or untracked files, use --force to delete it. git worktree remove protects work you have not committed. Open the folder and commit, stash or discard the changes, or rerun with --force if you are sure you do not need them. A locked worktree needs unlocking first (or --force twice).

Submodules. Git’s own documentation describes multiple worktrees as experimental where submodules are involved and does not recommend multiple checkouts of a repository that has them. In practice, run git submodule update --init in each new worktree, and expect git worktree move to refuse with working trees containing submodules cannot be moved or removed; remove then needs --force.

FAQ

Do worktrees use a lot of extra disk space?

Only for the checked-out files, plus a small index. The history is stored once and shared, so a worktree is much smaller than a second clone, apart from ignored files such as dependencies and build output.

Can two worktrees have the same branch checked out?

No; see the rule above. Use a detached checkout of the same commit, or a second branch.

Do stashes, hooks and config carry over?

Yes. The stash list is shared, because it is stored in refs/stash and all refs/ are shared; a stash made in one worktree can be applied in another. Hooks live in the shared .git/hooks folder by default, and the repository config is shared too. HEAD, the staging area and per-worktree refs such as an in-progress bisect are separate.

What happens to my commits when I remove a worktree?

Nothing. Branches and commits live in the shared repository and stay; only uncommitted changes in that folder are lost. Commits made on a detached HEAD need a branch first, or you will have to find them in the reflog.
