git log --first-parent explained

On a project where every change arrives through a merged pull request, git log on main interleaves every commit of every branch, so the history reads as a jumble of “fix typo” and “wip”. --first-parent follows only the line that main itself moved along: one merge commit per pull request, plus anything committed to main directly. This guide explains what the first parent is, how to read and search a mainline with it, how to see what one merge brought in, git bisect --first-parent, and the cases where it gives a misleading picture.

What “first parent” means

An ordinary commit has one parent, the commit before it. A merge commit has two (occasionally more), and their order is recorded. The first parent is the commit the branch was at when you merged: the branch you were on. The second parent is the tip of the branch you merged in. When a pull request is merged into main with a merge commit, the first parent is the previous main and the second is the pull request’s last commit.

git log -1 --format='%p %s' 9da5bef
7ec1913 c2e5549 Merge pull request #12 from ana/login
git log --oneline -1 9da5bef^1   # first parent: main before the merge
7ec1913 Bump version
git log --oneline -1 9da5bef^2   # second parent: the pull request's tip
c2e5549 Fix typo

Following only first parents from the tip of main walks back through every state main has been in, one step per merge or direct commit, and never wanders into a feature branch.

git log --first-parent

Our test repository has two pull requests merged into main, with three and two commits, plus one commit made on main directly:

git log --oneline --graph
*   85bfe9a Merge pull request #13 from ana/search
|\
| * bbcd8bb Search: debounce
| * d1822ce Add search box
|/
*   9da5bef Merge pull request #12 from ana/login
|\
| * c2e5549 Fix typo
| * 6e176dc Validate password
| * 81fca23 Add login form
* | 7ec1913 Bump version
|/
* d710cb5 Initial
git log --oneline --first-parent
85bfe9a Merge pull request #13 from ana/search
9da5bef Merge pull request #12 from ana/login
7ec1913 Bump version
d710cb5 Initial

Nine commits become four. Nothing is hidden from the merges themselves: the merge commit’s tree contains all of the pull request’s changes. With --graph it draws a single straight line. It combines with the other git log options as usual, for example --since, --author or --reverse; see the git log --graph guide for the formatting ones.

With a path, --first-parent changes what a merge’s diff is compared with: its first parent. So the merge itself is reported as changing the file, and the commits inside the pull request are not listed:

git log --oneline --first-parent -- f
9da5bef Merge pull request #12 from ana/login
d710cb5 Initial

The same applies to git blame --first-parent, which credits each line to the merge that brought it into main instead of to the original commit, and to git describe --first-parent, which counts only mainline commits since the tag (v1-3-g85bfe9a instead of v1-8-g85bfe9a in our test).

With --merges and --no-merges

git log --oneline --first-parent --merges
85bfe9a Merge pull request #13 from ana/search
9da5bef Merge pull request #12 from ana/login
git log --oneline --first-parent --no-merges
7ec1913 Bump version
d710cb5 Initial

--merges keeps only commits with more than one parent, so on a pull-request workflow the result is a list of merged pull requests, a good starting point for release notes (add v1.2.0..HEAD to limit it to one release). --no-merges is the opposite: the commits that landed on main without going through a merge. On a project where every change should be reviewed, that list is worth checking.

Without --first-parent, --merges would also list merges made inside feature branches, such as “Merge branch ‘main’ into login”, and --no-merges would list every commit of every pull request.

What one merge brought in

git log --oneline 9da5bef^1..9da5bef^2
c2e5549 Fix typo
6e176dc Validate password
81fca23 Add login form
git diff --stat 9da5bef^1 9da5bef
 f | 3 +++
 1 file changed, 3 insertions(+)

The range means “reachable from the pull request’s tip but not from main before the merge”, which is exactly the commits the merge added. git 2.53 also accepts the shorthand 9da5bef^-1, which lists the same commits plus the merge itself. The diff against the first parent shows the whole pull request as one change; git show --first-parent 9da5bef prints the same thing with the commit message. To compare two branches in this way before merging, see compare branches.

One branch or all branches

git log --first-parent starts from HEAD; name a branch to follow its line instead: git log --oneline --first-parent main. Each branch has its own first-parent line, and --all follows all of them at once. In our test, where the two feature branches had not been deleted after merging, git log --oneline --first-parent --all listed all nine commits again, because each feature branch’s own line contains its commits. For a clean mainline, name the branch rather than using --all, or delete merged branches (the ahead and behind guide shows how to find them).

git bisect --first-parent

git bisect finds the commit that introduced a bug by testing commits between a good and a bad one. On a merge-heavy history it can land you inside a half-finished pull request whose intermediate commits do not even build. With --first-parent (git 2.29 and later) it tests only mainline commits and names the merge that broke things:

git bisect start main d710cb5
Bisecting: 4 revisions left to test after this (roughly 2 steps)
git bisect reset
git bisect start --first-parent main d710cb5
Bisecting: 0 revisions left to test after this (roughly 1 step)
[9da5bef0d3905022d091796a2fe8e5082eafc518] Merge pull request #12 from ana/login
git bisect bad
git bisect good
9da5bef0d3905022d091796a2fe8e5082eafc518 is the first bad commit

Once you know the merge, you can bisect inside it if you need the exact commit: git bisect start 9da5bef^2 9da5bef^1 (bad is the pull request’s tip, good is main before the merge). Finish either session with git bisect reset.

When first parent misleads

  • Someone merged main into their copy of main. If a developer has local commits on main, runs git pull with merging, and pushes, the new merge’s first parent is their local commit and the previous shared main becomes the second parent. From then on, the first-parent line runs through their work, and the merges that landed on the shared main between their last pull and this one drop out of --first-parent output. Using git pull --rebase or --ff-only on shared branches, or only changing main through pull requests, avoids it.
  • A fast-forward merge leaves no merge commit. If a branch was merged with a fast-forward, its commits became part of the mainline directly, and --first-parent lists every one of them. Merging with --no-ff keeps the one-line-per-merge shape.
  • Squash and rebase merges. Hosting services that squash a pull request into one commit, or rebase it onto main, create no merge commits at all. --first-parent then changes nothing; with squash merges the history already has one commit per pull request.
  • Inside a feature branch, a “Merge branch ‘main’ into feature” commit has the feature branch as its first parent, so git log --first-parent feature shows your own work plus those merges, which is usually what you want.

First parent in Mergeline

Mergeline is a free, MIT-licensed git graph for VS Code. From version 0.12 its toolbar has a First parent checkbox that follows only the first parent of merges, as git log --first-parent does. On a mainline full of merged pull requests you see one commit per merge, not every commit of every branch.

  1. Tick First parent in the toolbar above the graph. The same switch is the setting mergeline.firstParentOnly (off by default), so it stays on until you untick it.
  2. Read the lines. Each branch shows its own first-parent line, and the commits a merge brought in are hidden behind that merge. Click a merge to see its details; its changed files are listed against its first parent, so they are everything the merge brought in.
  3. Search it. Find, including All history, searches the same view, so with First parent on it matches only commits on those lines, not the commits hidden inside merges. Untick First parent to search everything.

To limit the graph to one branch as well, as in git log --first-parent main, combine it with the branch filter from show only some branches.

FAQ

Does --first-parent hide changes?

It hides commits, not changes. Every change from a merged branch is in the merge commit’s tree, and the merge’s diff against its first parent shows all of it. What you lose is the step-by-step story inside the pull request.

How do I tell which parent is first?

git log -1 --format=%p <merge> lists the parents in order; the first hash is the first parent. git log --graph also draws the first parent straight down and the second off to the side.

Can I make --first-parent the default?

Not with a config setting for git log, but an alias does it: git config --global alias.mainline "log --oneline --first-parent", then git mainline.
