git commit --fixup and --autosquash: fix an earlier commit

You are three commits further on and notice that an older commit has a bug, a missing file or a bad message. Rather than stopping to rebase right now, you can record the correction as a fixup commit that names its target, keep working, and fold every such commit into place later with one rebase. This guide covers the four kinds of these commits, the --autosquash rebase that applies them, the config that makes it the default, what to do if the branch is already pushed, and how to undo it.

What a fixup commit is

A fixup commit is an ordinary commit whose subject line starts with fixup! followed by the subject of the commit it corrects, for example fixup! Add b. Nothing special happens when you make it: it sits on top of your branch like any other commit. The prefix only matters later, when a rebase with --autosquash reads it, moves the commit to just below its target in the todo list, and marks it to be melded in. The result is the history you would have had if the original commit had been right the first time.

This works well on a feature branch before review or before merging, when you want clean, self-contained commits but do not want to break your flow every time you spot a mistake.

Create one: git commit --fixup

Stage the correction, then name the commit it belongs to by hash (or any other reference git accepts, such as HEAD~2):

git log --oneline
6b59a1f Add c
ce4b2a6 Add b
085debd Add a
git add -u
git commit --fixup=ce4b2a6
git log -1 --format=%s
fixup! Add b

No editor opens; the message is generated for you. --fixup commits only what is staged. With nothing staged it stops with nothing to commit, working tree clean, and with changes that are only in your working files it stops with no changes added to commit. git add -u stages every change to files git already tracks (new files are left alone), or git commit -a --fixup=<commit> does both steps at once.

fixup!, squash! and amend!

Git has three more variations. They differ in what happens to the target’s message, and in what the autosquash rebase writes into the todo list:

Create withSubjectTodo commandResult
--fixup=<c>fixup! <subject>fixupThe changes go into the target; the target’s message stays as it is.
--squash=<c>squash! <subject>squashThe changes go into the target, and the new commit’s message is added to the target’s. Add a body with -m or in the editor.
--fixup=amend:<c>amend! <subject>fixup -CThe changes go into the target, and the message you write replaces the target’s.
--fixup=reword:<c>amend! <subject>fixup -COnly the target’s message changes. The commit is empty, even if you have staged changes.

Both amend: and reword: open the editor with amend! <subject> on the first line; leave that line alone and write the new message below it. They cannot be combined with -m (git stops with options '-m' and '--fixup:amend' cannot be used together). With reword:, anything you had staged is still staged afterwards, so it is not lost. If you only want to fix the message of the newest commit, git commit --amend is simpler; the edit a commit message guide covers both.

Fold them in: git rebase -i --autosquash

When you are ready, rebase from the parent of the oldest commit that has a fixup aimed at it. Here the oldest target is Add a, which is the first commit of the repository, so --root takes the place of a base:

git log --oneline
98af330 Unrelated later commit
eb5c37e amend! Add c
b901680 amend! Add a
c1e87df squash! Add b
6fffe0e fixup! Add b
6b59a1f Add c
ce4b2a6 Add b
085debd Add a
git rebase -i --autosquash --root     # if the oldest target is not the first commit: <target>^

The todo list opens already rearranged. Each fixup!, squash! and amend! commit has been moved under its target and given the matching command:

pick 085debd # Add a
fixup -C b901680 # amend! Add a
pick ce4b2a6 # Add b
fixup 6fffe0e # fixup! Add b
squash c1e87df # squash! Add b
pick 6b59a1f # Add c
fixup -C eb5c37e # amend! Add c # empty
pick 98af330 # Unrelated later commit

Usually you just save and close. The result has four commits: Add a with its new message, Add b with both fixes and the squash note appended to its message, Add c with its new message, and the unrelated commit unchanged.

Pick the base carefully. A target has to be inside the rebase to receive its fixup. Running the same rebase from HEAD~7 (which is Add a itself) leaves amend! Add a as a plain pick, so it stays in your history as a separate commit. Git matches a fixup to its target by subject, or by hash if what follows fixup! is a hash, so two commits with the same subject can confuse it; check the todo list before saving.

Two flags make it hands-free:

GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash --autostash <oldest target>^
  • GIT_SEQUENCE_EDITOR=: accepts the todo list without opening it (: is a shell command that does nothing). This is bash and zsh syntax.
  • --autostash stashes uncommitted changes before the rebase and puts them back afterwards. Without it, the rebase refuses to start on a dirty working tree.

A squash step still opens your editor so you can combine the two messages. To keep the message git prepares without editing it, add GIT_EDITOR=true as well; the squash! subject line itself is dropped and its body is kept. If a step conflicts, the rebase stops like any other: see continue, skip or abort a stopped rebase. The interactive rebase guide shows how to get the todo list in a VS Code tab instead of Vim.

Make it the default: rebase.autoSquash

git config --global rebase.autoSquash true

With this set, every git rebase -i rearranges fixup commits without needing the flag, and --no-autosquash turns it off for one run. In the git version tested here (2.53), the setting did not affect a plain git rebase <base> without -i; that rebase left the fixup commits as they were. Passing --autosquash explicitly to a non-interactive rebase did fold them in. Older git versions may behave differently, so check git rebase --help for yours.

Commits you already pushed

Folding fixups in rewrites every commit from the oldest target onward, so they all get new hashes. If the branch was already pushed, a normal push is refused:

git push
 ! [rejected]        main -> main (non-fast-forward)
git push --force-with-lease
 + 98af330...0358be4 main -> main (forced update)

--force-with-lease overwrites the remote branch only if it still points where your last fetch saw it, so it will not silently throw away commits someone else pushed in the meantime. To see beforehand whether a commit is already on a remote branch, run git branch -r --contains <commit>; any output means it has been pushed. Do not rewrite a shared branch such as main that others have pulled; there, leave the fix as an ordinary commit.

Undo an autosquash

A rebase records where your branch was before it started in ORIG_HEAD, so right after it finishes you can go back:

git reset --hard ORIG_HEAD

--hard overwrites uncommitted changes, so commit or stash them first. If you have since run another reset, rebase or merge, ORIG_HEAD has moved on; find the old position in git reflog instead, as the undo guide explains.

Do it in Mergeline

From Mergeline 0.10 you can create fixup commits and fold them in from the graph, picking the target by clicking it instead of copying a hash.

  1. Stage the fix in the Source Control view as usual (or skip this step and let Mergeline stage for you).
  2. Create the fixup. Right-click the commit you are correcting and choose Create fixup commit for this. It is offered on commits of the checked-out branch’s own line. Mergeline runs git commit --fixup=<that commit> with your staged changes; if nothing is staged, it offers to stage all changes to tracked files first (git add -u). The new fixup! commit appears at the top of the graph.
  3. Fold them in. When the checked-out branch has fixup!, squash! or amend! commits, the right-click menu of a commit on that branch shows Squash N fixup commits into their targets… (into its target when there is only one). It runs git rebase -i --autosquash --autostash from the parent of the oldest target, without opening an editor, so the base is chosen for you. It warns first if the commits are already on a remote branch.
  4. Check, then push or undo. Mergeline offers Undo after the squash. If the branch was already pushed, push it with git push --force-with-lease as above.

If a fixup conflicts with a commit between it and its target, the rebase stops and the bar above the graph shows it, with Continue, Skip and Abort; see the conflicts guide. Related: squash commits, edit a commit message and interactive rebase.
