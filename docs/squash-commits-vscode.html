How to squash commits in git and VS Code

Squashing combines several commits into one. You do it to turn “WIP”, “fix typo” and “actually fix it” into a single commit that says what changed, before a review or before landing a branch. Git has four ways to do it, from a full interactive editor to a two-command shortcut. This guide covers each, how to edit the rebase list in VS Code, and how to get your commits back if a squash goes wrong.

Squash the last N commits with git rebase -i

Interactive rebase replays your recent commits and lets you say what to do with each. Pass it the commit below the oldest one you want to change. HEAD~4 means “four commits back”, so this edits the newest four:

git log --oneline -5
f5903f4 WIP
96a32ce Handle empty rows
9fcf750 Fix typo
086aa72 Add CSV export
16cd613 Initial
git rebase -i HEAD~4

Git opens a todo list in your editor. Note that it runs oldest first, the reverse of git log (recent git versions also print a # before each subject):

pick 086aa72 Add CSV export
pick 9fcf750 Fix typo
pick 96a32ce Handle empty rows
pick f5903f4 WIP

Change the word at the start of a line to decide that commit’s fate. To fold the last three into the first:

pick 086aa72 Add CSV export
fixup 9fcf750 Fix typo
squash 96a32ce Handle empty rows
fixup f5903f4 WIP
CommandWhat it does
pick (p)Keep the commit as it is.
reword (r)Keep it, but stop to edit its message.
squash (s)Meld it into the commit above, and open the editor with both messages so you can combine them.
fixup (f)Meld it into the commit above and throw its message away. fixup -C keeps this commit’s message instead.
drop (d)Remove the commit. Deleting the line does the same.

Save and close the file and git replays the list. The first line must stay pick: a squash there fails with cannot 'squash' without a previous commit. You can also reorder lines to squash commits that are not next to each other, though moving commits past each other can cause conflicts. Deleting every line cancels the rebase. To include the very first commit of the repository, use git rebase -i --root.

If a step conflicts, fix the files, git add them and run git rebase --continue. git rebase --abort puts everything back the way it was before you started.

Edit the todo list in VS Code

Git opens the todo list in its configured editor, which is often Vim. To get it as a VS Code tab instead, tell git to use VS Code and to wait until you close the tab:

git config --global core.editor "code --wait"        # commit messages and the todo list
git config --global sequence.editor "code --wait"    # only the todo list
GIT_SEQUENCE_EDITOR="code --wait" git rebase -i HEAD~4   # just this once (bash, zsh)

Edit the git-rebase-todo tab, save it, and close it; the rebase continues when the tab closes. Use codium --wait in VSCodium and cursor --wait in Cursor. Alternatively, the VS Code setting git.terminalGitEditor makes the editor itself the git editor for commands run in its integrated terminal; restart the terminal after turning it on.

The shortcut: git reset --soft

When you simply want the last few commits to become one, you do not need a rebase at all:

git reset --soft HEAD~3
git commit -m "Add CSV export"

A soft reset moves the branch back three commits but keeps every change staged, so the next commit contains all of them. Nothing is replayed, so nothing can conflict. The old messages are gone, but git remembers where the branch was in ORIG_HEAD, so you can start from them: in bash or zsh, git commit --edit -F <(git log --format=%B --reverse HEAD..ORIG_HEAD) opens the editor with all three messages.

To squash a whole feature branch, reset to the point where it left main: git reset --soft $(git merge-base main HEAD), then commit. The undo guide explains the soft, mixed and hard modes.

Squash a whole branch while merging: git merge --squash

git switch main
git merge --squash feature
Squash commit -- not updating HEAD
git commit -m "Add CSV export"
git branch -D feature

This stages the combined changes of the whole branch on main without committing or recording a merge, and you commit once. It is what hosting platforms call “squash and merge”. Because no merge is recorded, git does not consider feature merged, so deleting it needs -D. The rebase vs merge guide compares this with an ordinary merge.

Fix as you go: --fixup and --autosquash

If you notice a mistake in an earlier commit, record the fix as a commit aimed at it:

git commit --fixup=086aa72        # creates "fixup! Add CSV export"
git rebase -i --autosquash main   # the todo list arrives with fixups already in place

--autosquash moves each fixup! commit under its target and marks it fixup, so you usually just save and close. Make it the default with git config --global rebase.autoSquash true. Variants: --squash=<commit> keeps the new message for editing, --fixup=reword:<commit> changes only the target’s message, and --fixup=amend:<commit> changes its content and message. To skip the editor entirely, GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash main accepts the list as is. The fixup and autosquash guide covers each variant in detail.

Pushed commits, and undoing a squash

Every method here except merge --squash rewrites history: the squashed commit is new, with a new hash. On commits only you have, that is harmless. If you already pushed the branch, a normal push is rejected and you must force-push. Use the safe form, which refuses if someone else pushed in the meantime:

git push --force-with-lease

Do not squash commits on a shared branch such as main that others have pulled. To undo a squash right after it finishes, run git reset --hard ORIG_HEAD (commit or stash other changes first, since --hard overwrites them). Later, find the old position in the reflog: the entry just below rebase (start) is your branch before the rebase.

git reflog
1c1ee26 HEAD@{0}: rebase (finish): returning to refs/heads/main
1c1ee26 HEAD@{1}: rebase (fixup): Add CSV export
...
086aa72 HEAD@{4}: rebase (start): checkout HEAD~4
f5903f4 HEAD@{5}: commit: WIP
git reset --hard f5903f4

Do it in Mergeline

The graph shows exactly which commits you are about to combine, so there is no HEAD~N counting.

  1. Interactive rebase: right-click the commit just below the oldest one you want to squash and choose Interactive rebase from here (terminal). Mergeline opens a terminal named Mergeline rebase and runs git rebase -i <that commit>; edit the todo list as above. Set core.editor or sequence.editor to code --wait first to edit it in a tab.
  2. Soft reset: right-click the newest commit you want to keep as it is, choose Reset “<branch>” to here… and pick Soft (keep changes staged). The uncommitted-changes row at the top now holds the combined changes; commit them from the Source Control view with one message.
  3. Squash merge: check out the target branch, right-click the other branch’s badge, choose Merge into “<branch>”… and pick Squash merge. The changes are staged for you to commit. Deleting the branch afterwards asks before force-deleting, because git does not see it as merged.
  4. Check and push: the graph updates when the repository changes (click Refresh if it has not). Right-click the branch and choose Push; if the branch was already on the remote, the push is rejected, so run git push --force-with-lease in the terminal.
