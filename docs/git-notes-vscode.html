git notes: add a note to a commit without changing its hash

Sometimes you want to write something on a commit after the fact: “deployed to production”, “reviewed by Bob”, a link to a CI run. Editing the message would change the commit’s hash and rewrite history. A git note is text attached to a commit from the outside, so the commit and its hash stay exactly as they were. This guide covers the commands, how notes show up in git log, sharing them (they are not pushed by default), what amend and rebase do to them, and notes in VS Code.

What a git note is

A note is a piece of text that git stores next to a commit, not inside it. The commit’s hash is computed from its content, message, author and parents; a note is none of those, so adding one leaves the hash alone:

git rev-parse --short HEAD
b24d436
git notes add -m "Deployed to staging"
git rev-parse --short HEAD
b24d436

Notes live under their own ref, refs/notes/commits by default. A ref is a name pointing at a commit, like a branch. This one points at a small history of its own that records every note change, so notes can be pushed, fetched and merged much like a branch. Because it is not under refs/heads/, it is not a branch and does not appear in git branch.

Add, replace, append, show, remove

Each commit has at most one note per notes ref. git notes add refuses to overwrite one unless you add -f:

git notes add -m "Deployed to production"
error: Cannot add notes. Found existing notes for object b24d436de4dde534aa5ef23bcb180f78294fe2fe. Use '-f' to overwrite existing notes
git notes add -f -m "Deployed to production"
Overwriting existing notes for object b24d436de4dde534aa5ef23bcb180f78294fe2fe
git notes append -m "Smoke tests passed"
git notes show
Deployed to production

Smoke tests passed
  • Without -m, git notes add and git notes append open your editor, as git commit does. -F <file> reads the text from a file.
  • append adds a blank line and the new text to the existing note, or creates the note if there is none.
  • Every command takes a commit as the last argument; without one it uses HEAD. git notes show HEAD~1 on a commit without a note printed error: no note found for object 6a3712a9342d9267a0ab55329d1f7b94668db9fa.
  • git notes list prints one line per note: the note’s own object id, then the commit it belongs to.
git notes list
b3d9e725bdfa420707330be79cf9958fd1e9b678 b24d436de4dde534aa5ef23bcb180f78294fe2fe
git notes remove HEAD
Removing note for object HEAD

Notes in git log

git log and git show print notes by default, under a Notes: heading after the message:

git log -1
commit b24d436de4dde534aa5ef23bcb180f78294fe2fe
Author: Ann Lee <ann@example.com>
Date:   Fri Nov 20 10:00:00 2026 +0100

    Fix session timeout

Notes:
    Deployed to production

    Smoke tests passed
  • --no-notes hides them.
  • git log --oneline does not show them; git log --oneline --notes does.
  • In your own --format, %N is the note text: git log --format='%h %s: %N' printed b24d436 Fix session timeout: Deployed to production followed by the rest of the note. A format without %N shows no note, even with --notes.
  • Notes in another ref are shown with --notes=<name>: git log --notes=review shows refs/notes/review under a Notes (review): heading. Setting core.notesRef changes which ref every git notes command and git log use by default.

Push and fetch notes

Notes stay on your machine unless you push them on purpose. A normal push sends branches; git ls-remote after git push origin main listed only HEAD and refs/heads/main. Push the notes ref by name:

git push origin refs/notes/commits
To ../origin.git
 * [new reference]   refs/notes/commits -> refs/notes/commits

Fetching is the same story. A fresh clone of that repository had no notes: git show-ref listed only branches, and git notes show HEAD said error: no note found. Fetch them explicitly:

git fetch origin 'refs/notes/*:refs/notes/*'
From …/origin
 * [new ref]         refs/notes/commits -> refs/notes/commits
git notes show HEAD
Deployed to production

Smoke tests passed

To get notes with every git fetch, add the refspec to the remote: git config --add remote.origin.fetch '+refs/notes/*:refs/notes/*'. After that, a plain git fetch origin brought in refs/notes/commits. The leading + lets the fetch overwrite your local notes ref, so notes you added locally and did not push are replaced by the remote’s.

If both sides added notes, the refs have diverged. Without the +, the fetch was refused with ! [rejected] refs/notes/commits -> refs/notes/commits (non-fast-forward), and the push was refused too. Fetch the remote’s notes into a separate ref and merge them: git fetch origin refs/notes/commits:refs/notes/origin/commits, then git notes merge refs/notes/origin/commits. When both sides had noted the same commit, the merge stopped with CONFLICT (add/add): Merge conflict in notes for object …; git notes merge -s union instead joined the two texts into one note.

Amend, rebase and cherry-pick

A note belongs to one commit hash. Amending, rebasing or cherry-picking creates new commits with new hashes, and by default the note does not come along: the old commit keeps it, and the new one has none. We tested each case on a commit with a note:

OperationDefault settingsWith notes.rewriteRef set
git commit --amendnote not copiednote copied
git rebase and git rebase -inote not copiednote copied
git cherry-picknote not copiednote not copied

The switch is notes.rewriteRef, which names the notes refs to carry over and has no value until you set one:

git config notes.rewriteRef refs/notes/commits

Two more settings, notes.rewrite.amend and notes.rewrite.rebase, are on by default but do nothing while notes.rewriteRef is unset. With it set, setting either to false stopped the copy for that command. For a single command, the environment variable GIT_NOTES_REWRITE_REF=refs/notes/commits did the same as the setting. To move a note by hand, for example after a cherry-pick, run git notes copy <old> <new>. In every case the old commit kept its note as well.

What people use notes for

  • Deploy markers. A deploy script runs git notes append -m "Deployed to production 2026-11-20" on the commit it shipped and pushes refs/notes/commits.
  • Review sign-off. “Reviewed by …” on a commit after it was merged, without amending a commit others already have.
  • CI results. A link to the build or the test summary. Keep these in their own ref, such as git notes --ref=ci add -m "…", so they do not mix with notes people write.
  • Corrections. A message that turned out to be wrong or incomplete: the note shows up next to it in git log.

Notes in VS Code

We searched the Git extension bundled with VS Code 1.147 (its package.json, its package.nls.json with the user-facing strings, and its code) for “notes” and found no mention of git notes. To add or read notes there, use the integrated terminal (Ctrl+`) with the commands above.

Notes in the Mergeline graph

Mergeline is a free, MIT-licensed git graph for VS Code. From version 0.15 it shows git notes and lets you add, edit and remove them.

  1. See which commits have a note. Rows with a note show a small “note” mark before the subject.
  2. Read it. Click the commit. The details pane shows the note under the message, with an Edit link.
  3. Add or edit. Right-click a commit and choose Add note…, or Edit note… if it already has one. An editor opens in the graph; save to write the note. Saving it empty removes the note.
  4. Remove. Right-click and choose Remove note.

Mergeline reads and writes only the default notes ref: refs/notes/commits, or the ref named in core.notesRef if you set it. It does not push or fetch notes; use the commands in Push and fetch notes.

Showing notes is Git Graph issue #475, opened in March 2021. When we checked on 20 November 2026 it was still open, with 19 thumbs-up.

FAQ

Does adding a note change the commit hash?

No. The note is stored outside the commit, in refs/notes/commits. In our test the hash was b24d436 before and after.

Why can’t my teammates see my notes?

Because notes are not pushed with branches and not fetched by default. Push with git push origin refs/notes/commits; they fetch with git fetch origin 'refs/notes/*:refs/notes/*'.

Where did my note go after a rebase?

It is still on the old commit. Rebase made a new commit, and without notes.rewriteRef the note was not copied. Find the old hash with git reflog and run git notes copy <old> <new>, then set git config notes.rewriteRef refs/notes/commits for next time.

Can a commit have more than one note?

One per notes ref. Use git notes append to add to it, or a separate ref with --ref=<name> for a different kind of note.
