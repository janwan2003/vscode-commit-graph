The git stash guide: push, apply, pop, drop and branch

You are halfway through a change when you need a clean working tree: an urgent fix on another branch, a pull that refuses to run, or a quick test of the code as it was. git stash takes your uncommitted changes, saves them away, and gives you back a clean checkout. Later you put them back. This guide covers the whole lifecycle of a stash and the few options that save you from surprises.

Saving: git stash push

git stash                              # same as git stash push
git stash push -m "half-done search"    # with a message you will recognise later

By default a stash saves changes to tracked files, both staged and unstaged, and then resets them to match HEAD. Brand-new files that you have never added are left where they are. That is the most common stash surprise. The options that change what is saved:

  • -u (--include-untracked) also stashes untracked files. -a (--all) adds ignored files too, which is rarely what you want because it sweeps up build output and node_modules.
  • git stash push -- src/search.ts src/search.css stashes only those paths.
  • -p (--patch) asks hunk by hunk what to stash.
  • --staged stashes only what is staged (git 2.35 and later).
  • --keep-index stashes everything but leaves the staged changes in place, handy for testing exactly what you are about to commit.

You may also see git stash save "message" in older tutorials. It still works but is deprecated in favour of git stash push -m, which also accepts paths.

Listing and inspecting

git stash list
stash@{0}: On main: half-done search
stash@{1}: WIP on feature/export: 72c5f10 Fix date parsing in log view

The newest stash is always stash@{0}, and the numbers shift every time you add or remove one, so check the list before you name a stash by number. Stashes made without -m are labelled WIP on <branch> plus the commit they were made on. Each stash also remembers the branch it came from, but you can apply it anywhere.

git stash show stash@{1}        # files changed, with a summary of lines
git stash show -p stash@{1}     # the full diff
git restore --source=stash@{1} -- src/export.ts   # pull one file out of a stash

Apply vs pop

git stash apply                # reapply stash@{0}, keep it in the list
git stash apply stash@{2}      # reapply a specific one
git stash pop                  # reapply stash@{0} and remove it from the list

apply leaves the stash in the list, so you can apply the same changes to several branches or try again if something goes wrong. pop is apply followed by drop, and is what you want most of the time.

Both can hit conflicts if the files changed since you stashed. Resolve them as you would any merge conflict and git add the files. When pop hits a conflict, the stash is not dropped, so nothing is lost; once you are happy, remove it yourself with git stash drop.

By default, applying puts everything back as unstaged changes, even what was staged. Add --index (git stash pop --index) to restore the staged/unstaged split exactly.

Drop and clear

git stash drop                 # delete stash@{0}
git stash drop stash@{3}       # delete a specific one
git stash clear                # delete all stashes, without asking

Stashes are easy to forget. A list of twelve WIP on main entries from last spring is a sign some of them can go. Look at each with git stash show -p before dropping it.

Turning a stash into a branch

git stash branch search-wip stash@{0}

This creates a new branch starting at the commit you were on when you made the stash, checks it out, applies the stash (restoring what was staged), and drops the stash if that succeeded. Because the branch starts exactly where the changes were made, it applies cleanly even when your original branch has moved on and a plain pop would conflict. It is also the right move when the “quick experiment” in a stash has turned into real work that deserves commits.

Recovering a dropped stash

A stash is stored as a commit, so dropping one removes the reference to it, not the data, until git garbage-collects it. git stash drop and a successful pop both print the hash:

Dropped stash@{0} (5d8e2f4a9c1b7e3d6f0a2b4c8e1d3f5a7b9c0d2e)
git stash apply 5d8e2f4a9c1b7e3d6f0a2b4c8e1d3f5a7b9c0d2e

If that output has scrolled away, ask git for commits that nothing points to and look for the stash-style messages:

git fsck --no-reflog | awk '/dangling commit/ {print $3}' \
  | xargs git log --no-walk --oneline
# look for "WIP on ..." or "On <branch>: ..." and apply that hash

When not to stash

  • The interruption will take a while. Commit the work in progress instead (git commit -m "wip"), and later undo the commit with git reset HEAD~1 to keep the changes. A commit lives on its branch, where you will find it again; a stash is easy to forget.
  • You need both versions at once. git worktree add ../hotfix main checks out main in a second folder, so you can fix a bug there without touching your current changes at all.

Do it in Mergeline

Because a stash is a commit, Mergeline draws each one as its own node, attached to the commit it was made on. You can see at a glance which stashes are old, and which branch each belongs to.

  1. Create a stash: right-click the Uncommitted changes row at the top of the graph and choose Stash changes… (it includes untracked files and asks for an optional message). Stashes made in the terminal or from VS Code’s Source Control view show up too; the graph refreshes on its own.
  2. Use it: right-click the stash and choose apply, pop, drop, or Create branch from stash, which runs git stash branch with a name you choose. Dropping asks for confirmation first.
  3. Hide them when you do not need them with the mergeline.showStashes setting. The uncommitted-changes row (mergeline.showUncommitted) shows what you have not stashed or committed yet.
