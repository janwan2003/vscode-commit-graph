Update a branch without checking it out

You are working on feature and want your local main to match the server, perhaps to rebase onto it or to start a new branch from it. The usual route is to stash, switch to main, pull and switch back, which also rewrites your working files twice and can trigger a rebuild. Git can move main directly instead, as long as the move is a fast-forward: main has no commits of its own and only needs to catch up. This guide covers git fetch origin main:main, the two errors it gives and what they mean, an offline variant, why git branch -f is riskier, and how to pull a different branch into the one you are on.

We ran every command on this page with git 2.53, using a local bare repository as origin and a second clone to push from, and quote the output we saw. Paths in error messages are from that test.

git fetch origin main:main

The main:main part is a refspec: <branch on the remote>:<branch here>. Without a refspec, git fetch only updates remote-tracking branches such as origin/main. With one, it also writes the fetched commit into your local branch main, but only if that is a fast-forward:

git switch feature
git fetch origin main:main
From /tmp/mlg/origin
   c598fd4..a979549  main       -> main
   c598fd4..a979549  main       -> origin/main

The first line is your local main moving forward; the second is origin/main, which git updates as well while it is at it. Your current branch, your working files and the index are not touched. If main is already up to date, the command prints nothing and exits successfully.

The two names do not have to match: git fetch origin release/2.4:release updates a local release from the remote’s release/2.4. If the remote has no such branch, git stops with fatal: couldn't find remote ref <name> and updates nothing, including the other refspecs on the same command line.

“[rejected] main -> main (non-fast-forward)”

git fetch origin main:main
From /tmp/mlg/origin
 ! [rejected]        main       -> main  (non-fast-forward)
   a979549..6106665  main       -> origin/main

Your local main has at least one commit that the server’s main does not, so moving it would drop that commit. Git refuses, leaves main where it was and exits with status 1. Note the second line: origin/main was still updated, so git log --oneline origin/main..main now shows exactly the commits that blocked it.

What to do depends on those commits. If you want to keep them, check main out and pull with a merge or a rebase (which one). If they were a mistake, for example commits you meant to make on a feature branch, move them to a branch first with git branch my-work main, then reset main as described under git branch -f. The ahead and behind guide shows how to see this situation coming.

“refusing to fetch into branch … checked out at”

git switch main
git fetch origin main:main
fatal: refusing to fetch into branch 'refs/heads/main' checked out at '/tmp/mlg/me'

Fetching into the branch you are on would move the branch but leave your working files and index at the old commit, so every change since would look like something you had undone. Git refuses, and fetches nothing. On the current branch use git pull --ff-only (or a plain git pull) instead.

The same error appears for a branch that is checked out in another worktree, with that worktree’s path: fatal: refusing to fetch into branch 'refs/heads/main' checked out at '/tmp/mlg/wt'. Run git worktree list to see where, then pull inside that folder. The worktree guide explains why a branch can only be checked out once.

git fetch has an --update-head-ok flag that disables this check. It exists for git pull’s own use; running it yourself produces exactly the out-of-step working tree the check is there to prevent.

Without the network: git fetch . origin/main:main

git fetch                        # once, from the server
git fetch . origin/main:main
From .
   ef89be6..c598fd4  origin/main -> main

The . is the current repository used as a remote, so this fetches from yourself: it fast-forwards main to your existing origin/main without contacting the server. It follows the same rules. A branch with its own commits gives ! [rejected] origin/main -> main (non-fast-forward), and a checked-out branch gives the “refusing to fetch” error. It is handy when you have just fetched, are offline, or want to fast-forward one local branch to another, such as git fetch . feature:main.

git branch -f and +main:main

git branch -f main origin/main
git fetch origin +main:main
 + a4255fe...c598fd4 main       -> main  (forced update)

Both move main to the remote’s commit whether or not it is a fast-forward. If main had commits of its own, they are no longer on any branch, with no question and no warning other than the (forced update) note. They are not deleted straight away: git reflog main lists where main pointed before, and the undo guide shows how to get them back. Use these only when you have checked, for example with git log --oneline origin/main..main, that there is nothing to lose.

git branch -f also refuses the current branch, with a different message: fatal: cannot force update the branch 'main' used by worktree at '/tmp/mlg/me'. When the new start point is a remote-tracking branch, it may also set the branch’s upstream (ours printed branch 'main' set up to track 'origin/main'.).

Pull another branch into yours

The opposite task, bringing the server’s main into the branch you are on, is a pull with an explicit branch:

git switch feature
git pull --no-rebase origin main
From /tmp/mlg/origin
 * branch            main       -> FETCH_HEAD
Merge made by the 'ort' strategy.

This fetches main and merges it into feature; your local main is not changed. Writing it as two steps, git fetch origin main and then git merge origin/main, gives the same result and lets you look at what arrived before merging. Use --rebase instead of --no-rebase to replay your commits on top. Without either, and without pull.rebase configured, git 2.53 stops on diverged branches with fatal: Need to specify how to reconcile divergent branches.

Do it in Mergeline

Mergeline is a free, MIT-licensed git graph for VS Code. From version 0.12 both tasks above are one right-click in the graph.

  1. Update a branch you are not on. Right-click a local branch that is not checked out and tracks a remote branch, and choose Update from origin/… (fast-forward) (for main, Update from origin/main (fast-forward)). Mergeline runs git fetch origin main:main for it, using the remote and branch the branch tracks. Your current branch and files are not touched.
  2. If it cannot fast-forward, because the branch has commits of its own, nothing changes, and Mergeline says so and suggests checking it out and pulling (merge or rebase) instead. As with the command line, origin/… itself may still have moved.
  3. Pull a remote branch into yours. Right-click a remote branch, such as origin/main, and choose Fetch and merge into “feature” (pull)…, where the name in quotes is your current branch. Mergeline fetches that branch first, so you merge what is on the server now rather than what you fetched last time, then offers the usual merge choices: fast-forward, --no-ff or --squash.

Before you use either, the branch badges show whether there is anything to do: ↓N means N commits to pull as of your last fetch (see ahead and behind in Mergeline). On the branch you have checked out, use Pull from its menu; the update item is offered only on other branches, and not on a branch whose upstream was deleted. Fetch and merge needs a checked-out branch to merge into, so it is unavailable on a detached HEAD.

FAQ

Is git fetch origin main:main safe?

Yes, in the sense that it cannot lose commits: without a leading + it only ever fast-forwards, and it never touches the branch you are on or your working files. The worst case is the [rejected] line, after which nothing has changed.

Why not just git pull into main from another branch?

git pull always merges or rebases into the current branch. git pull origin main while on feature merges main into feature; it does not update your local main.

Do I even need a local main?

Often not. You can rebase onto or branch from origin/main directly after a git fetch: git rebase origin/main, or git switch -c new-work origin/main. A local main that you never update is what produces “behind by 40 commits” messages.
