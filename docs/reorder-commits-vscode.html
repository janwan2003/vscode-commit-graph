How to reorder commits in git and VS Code

Commit order matters more than it seems. A reviewer reads a branch top to bottom, a refactor reads better before the feature that needs it, and two commits you want to squash have to sit next to each other first. Git can change the order of commits on your branch by replaying them in a new sequence. This guide shows how, what it does to the commits, why it sometimes conflicts, and how to put things back.

Reorder with git rebase -i

Start an interactive rebase from the commit just below the oldest one you want to move. For the newest three:

git log --oneline -4
5974a6f C: add three
485fdce B: add b
cee752e A: add two
3c2e146 Base
git rebase -i HEAD~3

The todo list lists the commits oldest first, the reverse of git log. Git applies them from top to bottom, so to reorder commits you reorder lines. Cut and paste them, keeping the word pick at the start:

pick cee752e # A: add two
pick 5974a6f # C: add three
pick 485fdce # B: add b

Save and close. Git replays the commits in the new order and the branch now ends with B. Leave a line out and that commit is dropped, so move lines rather than retyping them. If the editor is Vim and you would rather use VS Code, see setting the editor. Rebase refuses to start with uncommitted changes (cannot rebase: You have unstaged changes); --autostash stashes them and puts them back afterwards.

What changes, and pushed commits

A commit’s hash depends on its parent, so every commit from the first moved line onward gets a new hash. Lines above it that you left alone keep their hashes: in the example, A is still cee752e. Messages, authors and author dates are kept; the committer date becomes now.

If you only changed the order and nothing conflicted, the final files are identical. git diff ORIG_HEAD HEAD prints nothing, which is a quick way to confirm it.

If the commits were already pushed, the remote still has the old order and a plain push is rejected. Push with git push --force-with-lease, which refuses if someone else pushed to the branch in the meantime. Do not reorder commits on a shared branch such as main: everyone who pulled the old order would have to reconcile it with the new one.

When the moved commits conflict

Each commit is stored as a snapshot, but git replays it as a change to its parent. When two commits touch the same lines, or lines right next to each other, swapping them means applying a change to text that does not look the way it did when the change was made. Git then stops:

CONFLICT (content): Merge conflict in a.txt
error: could not apply 5974a6f... C: add three

Here C appended a line after the one A added, so C cannot go first without help. Resolve the file as it should look at this point in the new order, git add it and run git rebase --continue. Expect to resolve the same spot again when the other commit is applied. If that is more work than the new order is worth, git rebase --abort restores the branch exactly. The conflict guide walks through continue, skip and abort in detail.

Commits that change different files, or distant parts of the same file, reorder without any conflict.

The alternative: cherry-pick onto a new branch

If you would rather not touch the original branch until the result is right, build a new one. Start from the commit below the ones you want to move and pick them in the order you want; cherry-pick applies them in the order you list them:

git switch -c reordered cee752e
git cherry-pick 5974a6f 485fdce
git diff main reordered            # no output: same content, new order

Conflicts stop the cherry-pick the same way and are resolved with git cherry-pick --continue. When you are happy, point your branch at the new commits from the reordered branch with git branch -f main reordered, then git switch main. The old branch is untouched until that last step, so giving up just means deleting reordered.

Undo a reorder

Right after a rebase finishes, ORIG_HEAD points at the branch as it was before the rebase started (we checked this with git 2.53, for both a plain and an interactive rebase):

git reset --keep ORIG_HEAD

--keep refuses rather than overwrite uncommitted changes. ORIG_HEAD is replaced by the next reset, rebase or merge, so if you have done anything since, find the old tip in git reflog: it is the entry just below rebase (start). The undo guide explains the reflog. If you already force-pushed the new order, reset and force-push again.

Do it in Mergeline

From Mergeline 0.7 you can move a commit one step at a time from the graph, without a todo list.

  1. Right-click a commit on the checked-out branch and choose Move commit up (newer) or Move commit down (older). The commit swaps places with its neighbour. The menu items work on commits of the current branch (following first parents from HEAD back to the first merge commit); merge commits and commits on other branches are refused with a reason. To move a commit further, repeat.
  2. Mergeline runs the rebase for you. It writes the todo list itself and runs git rebase -i with --autostash, so no editor opens and uncommitted changes are kept. It warns first if the commit is already on a remote-tracking branch, because you would need to force-push.
  3. If the two commits conflict, the rebase stops and a bar at the top of the graph shows it, with Continue, Skip, Abort and Source Control. Resolve and stage the files, then press Continue, or press Abort to put the branch back.
  4. Undo in one click. When the move finishes, the notification offers Undo, which puts the branch back with git reset --keep.

The same menu can edit a commit message, squash or drop a commit. For several moves at once, use an interactive rebase.
