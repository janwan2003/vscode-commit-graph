Git rebase vs merge: when to use each

Merge and rebase solve the same problem: your branch and main have both moved on, and you want to bring them together. They differ in what they leave behind. A merge keeps history exactly as it happened and records the join. A rebase rewrites your commits so history reads as if you had started from the latest main. Neither is “right”; each fits different situations, and most teams use both.

The starting point

You branched feature from main at commit E and made three commits. Meanwhile two commits landed on main:

          A---B---C  feature
         /
    D---E---F---G  main

What merge does

git switch main
git merge feature

Git creates a new merge commit M with two parents, G and C. Nothing that already existed changes:

          A---B---C
         /         \
    D---E---F---G---M  main

If main had not moved since you branched, git would do a fast-forward instead: it simply moves the main label up to C and creates no merge commit. Two flags control this:

  • git merge --no-ff feature always creates a merge commit, so the feature stays visible as a group in the graph.
  • git merge --ff-only feature refuses to merge unless a fast-forward is possible. It is a good default for git pull on branches you never commit to directly: git config --global pull.ff only.

There is also git merge --squash feature, which stages the combined changes of the whole branch without committing or recording a merge. You then run git commit to make one ordinary commit. Hosting platforms call this “squash and merge”. The graph will not show that feature was merged, so delete the branch afterwards with git branch -D feature (capital -D, because git cannot tell it was merged).

What rebase does

git switch feature
git rebase main

Git sets your three commits aside, moves feature to the tip of main, and replays each change on top, one at a time:

                  A'--B'--C'  feature
                 /
    D---E---F---G  main

A', B' and C' contain the same changes as A, B and C, but they are new commits with new hashes, because their parent changed. The originals still exist until git garbage-collects them, which is why a rebase can be undone (see below). Now git switch main and git merge feature is a fast-forward, and history is a straight line.

An interactive rebase goes further and lets you edit the commits as they are replayed: reorder them, squash fixups together, reword messages or drop one. The squash guide walks through the todo list step by step.

git rebase -i main          # edit the todo list: pick, reword, squash, fixup, drop
git commit --fixup=<hash-of-B>  # mark a new commit as a fix for B ...
git rebase -i --autosquash main   # ... and have rebase fold it in for you

To keep a feature branch current without merge commits every time you pull, use git pull --rebase, or make it the default with git config --global pull.rebase true.

When to use which

SituationUseWhy
Bringing the latest main into your own, unshared feature branchRebaseYour branch stays a clean line on top of main, and reviewers see only your changes.
Tidying your commits before opening a pull requestInteractive rebaseSquash “fix typo” commits so each remaining commit makes sense alone.
Landing a finished feature on mainMerge (often --no-ff) or squash, per team conventionA merge commit records when and how the feature arrived and is easy to revert as a unit.
A branch other people have pulled and build onMergeRebasing it would rewrite commits under their feet.
Long-lived release or maintenance branchesMerge (or cherry-pick specific fixes)Their history is shared and should never be rewritten.
You want to know exactly what happened, in orderMergeMerges never change existing commits.

The one rule: do not rebase commits other people have

Rebasing replaces commits. If a teammate already has the old ones, their branch and yours now disagree about history, and the next pull produces duplicated commits and confusing conflicts. Rebase freely on branches only you use. If you rebase a branch you have already pushed for review, you must force-push it, and you should use the safe form:

git push --force-with-lease

--force-with-lease refuses to overwrite the remote branch if it contains commits you have not seen, for example a fix a reviewer pushed. Plain --force would silently delete them.

Conflicts

A merge shows you all conflicts once, in a single step. A rebase replays commit by commit, so you may resolve conflicts several times, but each one is smaller and in the context of a single change. The commands to know:

# during a merge
git merge --abort           # give up, back to before the merge
git add <file> && git commit   # after resolving

# during a rebase
git add <file> && git rebase --continue
git rebase --skip           # drop the commit being replayed
git rebase --abort          # give up, branch restored to where it was

If you rebase often and keep resolving the same conflict, enable git config --global rerere.enabled true. Git then records how you resolved a conflict and reapplies that resolution the next time it sees the same one.

Undoing either one

Both merge and rebase save the previous tip of your branch in ORIG_HEAD. Right after either finishes, this puts the branch back:

git reset --hard ORIG_HEAD

This also discards uncommitted changes in your working tree, so commit or stash them first. If you have done other things since, find the old position in git reflog instead; the undo guide walks through it. To undo a merge that has already been pushed, do not reset: revert it with git revert -m 1 <merge-commit>.

Do it in Mergeline

The graph shows the before and after, so you can check that the result is what you meant.

  1. Merge: check out the branch you want to merge into (the current branch has a bold badge with a ●), then right-click the other branch’s badge, or any commit, and choose merge into current. The new merge commit appears at the top with both lanes joining.
  2. Rebase: check out your feature branch, right-click main (or any commit) and choose rebase current onto. Your commits move to the top of that lane with new hashes.
  3. Interactive rebase: right-click the commit just below the oldest one you want to edit and choose the interactive rebase action. It runs git rebase -i from that commit in the integrated terminal so you can edit the todo list. Set git config --global core.editor "code --wait" to edit it in a tab.
  4. Conflicts: resolve them in the editor as usual. The uncommitted-changes row at the top of the graph shows the work in progress. Then continue or abort with the commands above and click Refresh.
  5. Push: right-click the branch and choose push. If you rebased a branch that was already on the remote, a normal push is rejected; run git push --force-with-lease in the terminal instead. Mergeline asks before every action and uses a modal confirmation for destructive ones.
