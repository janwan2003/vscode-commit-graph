Verify signed commits in git

A signed commit carries a cryptographic signature made with its author’s private key. Anyone holding the matching public key can check that the commit was made by that key and has not been altered since. Git can sign with GPG (the default), with an SSH key, or with an X.509 certificate, and in every case it checks signatures with keys on your machine: it never asks a server. This guide covers git verify-commit, git log --show-signature, every %G? status letter and what produced it in our tests, setting up GPG and SSH so that checking works, the errors you will meet, and refusing to merge unsigned work.

We ran every command on this page with git 2.53, GnuPG 2.4 and OpenSSH 10.2 in throwaway repositories and keyrings, and quote the output we saw. Dates and key IDs are trimmed.

Check one commit

git verify-commit HEAD
gpg: Signature made Fri Nov 20 16:20:56 2026 CET
gpg:                using EDDSA key 2BD8F875D24DBF9D345187DDE44F242AD0DFD2BD
gpg: Good signature from "Ana <ana@example.com>" [ultimate]
git log -1 --show-signature          # the same lines, above the usual log entry

git verify-commit prints the verifier’s report and sets its exit status, which is what you want in a script or CI job. For an unsigned commit it prints nothing and exits with status 1, so check the status rather than the output. --show-signature works with git log and git show; setting log.showSignature true turns it on for every log, at the cost of running a verification per commit.

The signature lives in the commit object itself, in a gpgsig header, which is why changing anything in the commit breaks it. git cat-file commit HEAD shows it: -----BEGIN PGP SIGNATURE----- for GPG, -----BEGIN SSH SIGNATURE----- for SSH.

The %G? letters

In a --format string, %G? gives one letter per commit, %GS the signer’s name, and %GK the key ID (for SSH, the key’s fingerprint). We produced every letter on purpose; the right-hand column is what the verifier said:

LetterMeaningHow we got it
GGood signature from a key you trustGPG: Good signature from "Ana <ana@example.com>" [ultimate]. SSH: Good "git" signature for ana@example.com with ED25519 key SHA256:…
UGood signature, but the key’s owner is not confirmedGPG: imported the key without trusting it, [unknown] and WARNING: This key is not certified with a trusted signature!. SSH: a key not in the allowed signers file, No principal matched.
XGood signature that has expiredGPG key set to make signatures valid for one day: Expired signature from …
YGood signature made by a key that has since expiredGPG key with a one-year lifetime, checked after it ended: Note: This key has expired!
RGood signature made by a key that has since been revokedImported the key’s revocation certificate: WARNING: This key has been revoked by its owner!
BBad signature: the commit does not match itEdited a signed commit’s message by hand. GPG: BAD signature from …. SSH: Signature verification failed: incorrect signature
ESigned, but cannot be checkedGPG without the signer’s public key: Can't check signature: No public key
NNo signature, or one git could not even try to checkAn unsigned commit; but also an SSH-signed commit with no allowed signers file, and any signed commit when gpg.program could not be run (see below)

Exit statuses differ more than the letters suggest. git verify-commit exited with 0 for G and, with GPG, also for U; it exited with 1 for an SSH U and for X, Y, R, B, E and N. If your script needs a trusted signature, test the letter, not just the exit status.

With SSH keys, X, Y and R did not appear in our tests. An allowed signers entry whose valid-before date had passed gave U, with key has expired in the output, and a key listed in gpg.ssh.revocationFile gave B with Could not verify signature.

GPG: importing and trusting keys

gpg --import ana.asc                 # the signer's public key, from them or their key server
git log --format='%h %G? %GS' -1
1006458 U Ana <ana@example.com>
gpg --lsign-key ana@example.com      # vouch for it locally, after checking the fingerprint
git log --format='%h %G? %GS' -1
1006458 G Ana <ana@example.com>

Without the public key, the result is E. After a plain import, it is U: the signature is mathematically good, but GPG has no reason to believe the key belongs to the person named in it. That is GPG’s web of trust. --lsign-key signs their key with yours, locally and never published, so you need a key of your own first; in a keyring without one, it changed nothing and the commit stayed U. Before signing the key or setting its owner trust with gpg --edit-key <key> and trust, compare the fingerprint, shown by gpg --fingerprint ana@example.com, with one the person gave you through another channel. Your own key is ultimately trusted from the start, which is why your own commits show G.

An expired key (Y) or an expired signature (X) does not mean the commit is forged; the signature was good when it was made. A revoked key (R) is different: its owner says it should no longer be relied on, possibly because it was stolen, so treat those commits with suspicion until you know why.

SSH: the allowed signers file

Signing with the SSH key you already use for pushing avoids GPG altogether:

git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git commit -S -m "Signed with SSH"       # or: git config --global commit.gpgSign true

Checking SSH signatures needs a list of which key belongs to whom, because an SSH key, unlike a GPG key, does not contain its owner’s identity. Until you configure one, every check stops with:

error: gpg.ssh.allowedSignersFile needs to be configured and exist for ssh signature verification

The file has one line per key: the signer’s email, then the public key as it appears in a .pub file. Start it with your own key:

mkdir -p ~/.config/git
echo "ana@example.com $(cat ~/.ssh/id_ed25519.pub)" >> ~/.config/git/allowed_signers
git config --global gpg.ssh.allowedSignersFile ~/.config/git/allowed_signers
git log --format='%h %G? %GS' -1
2e48a75 G ana@example.com

Add a line for each colleague whose commits you want to check, with the public signing key they gave you. A key that is not in the file gives U and No principal matched.; the signature is valid, git just cannot say who made it. Git looks the key up in the file to name the signer, and does not compare that name with the commit’s author: a commit authored as ana@example.com but signed with a key listed for bob@example.com showed G bob@example.com. Compare %GS with %ae yourself if that matters. Options such as valid-before="20270101" can go before the key to limit when it counts.

An N is not proof that a commit is unsigned. Without the allowed signers file, git 2.53 printed the error above and then reported N for a commit that was SSH-signed, and --show-signature said No signature. The same happened for GPG-signed commits when gpg.program pointed at a program that did not exist (fatal: cannot exec '…': No such file or directory). To tell for sure, look for the gpgsig header in git cat-file commit <commit>. And when we pointed gpg.ssh.allowedSignersFile at a file that did not exist, git printed no error at all and reported U, so check the path if every SSH signature comes back untrusted.

The third format, X.509 (gpg.format x509), uses gpgsm and your organisation’s certificates, and is verified the same way with gpgsm’s trust settings.

Signing errors

MessageCause
error: gpg failed to sign the data … gpg: signing failed: No secret key … fatal: failed to write commit objectuser.signingkey names a GPG key you do not have the private half of. gpg --list-secret-keys --keyid-format long shows the ones you do.
error: user.signingKey needs to be set for ssh signinggpg.format is ssh but no key is configured.
error: Couldn't load public key <path>: No such file or directory?The path in user.signingkey is wrong. Point it at the .pub file.

A GPG error that mentions the terminal or pinentry usually means GPG wanted to ask for your passphrase and had nowhere to do it, which is common when committing from an editor. Running export GPG_TTY=$(tty) in your shell profile, or unlocking the key once in a terminal, typically fixes it.

Refuse unsigned merges

git merge --verify-signatures unsigned
fatal: Commit 5e98bb5 does not have a GPG signature.
git merge --verify-signatures signed2
Commit 0b2f673 has a good GPG signature by Ana <ana@example.com>
Fast-forward

--verify-signatures, on git merge and git pull, refuses unless the tip commit of what you are merging has a good signature from a trusted key; an untrusted one gave fatal: Commit 0b2f673 has an untrusted GPG signature, allegedly by Ana <ana@example.com>. It checks only the tip, not every commit underneath it. To check a whole range, loop over git log --format='%h %G?' main..feature and fail on anything but G.

Signatures in Mergeline

Mergeline is a free, MIT-licensed git graph for VS Code. From version 0.12, the details pane shows a commit’s signature when you click the commit, so you do not have to run git verify-commit on each one.

  1. Click a commit in the graph. If it is signed, its details show the result, with the signer and key when git reports them.
  2. Read the status. The possible results are Good signature, good but from an untrusted key, expired (the signature, or the key that made it), signed with a revoked key, a BAD signature, or could not be checked. They correspond to the %G? letters above.
  3. If it could not be checked, your machine lacks the signer’s public key, or for SSH the allowed signers file. Set them up as described in GPG keys or the allowed signers file, then select the commit again. Unlike a bare %G?, Mergeline recognises an SSH-signed commit even when the allowed signers file is missing and says it could not be checked, instead of showing nothing.

Git does the checking, with your own GPG keyring and SSH allowed signers file; Mergeline only shows the answer and sends nothing anywhere. Unsigned commits show nothing, so the pane stays uncluttered on repositories that do not sign. Clicking a file in the details opens its diff, as described in the review guide.

FAQ

GitHub says “Verified”, but git says untrusted. Which is right?

Both, about different questions. A hosting service checks the signature against the keys uploaded to the author’s account there. Your git checks against your own keyring or allowed signers file, which knows nothing about that account until you add the key. Import the key and confirm its fingerprint to get the same answer locally.

Does a signature prove the commit is safe?

No. It proves which key made the commit and that it has not changed since. It says nothing about whether the code is correct, and a good signature from a stolen key still checks out as good until the key is revoked.

Do rebasing or cherry-picking keep signatures?

No. They create new commits, and a signature covers the exact commit it was made for. The new commits are signed only if you sign them, for example with commit.gpgSign true set or git rebase -S.
