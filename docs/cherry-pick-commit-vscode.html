How to cherry-pick a commit in VS Code

You fixed a bug on a feature branch and the fix is needed on main or a release branch today, without the rest of the feature. That is what cherry-pick is for. It takes the change one commit made and applies it to the branch you are on, as a new commit. This guide covers the command and its useful options, what to do when it conflicts, and how to do it from VS Code.

What cherry-pick does

Git works out what a commit changed compared with its parent, and applies that change to your current branch. It then makes a new commit with the same message and author. The new commit has a different hash, because it has a different parent.

Two things follow from that. First, the original commit stays where it was; nothing is moved. Second, the same change now exists twice in history. If the two branches are merged later, git usually notices the change is already there, but it can conflict if the code around it has changed. So cherry-pick is best for a few specific commits, like a fix for a release branch. If you want everything on a branch, merge or rebase instead; see rebase vs merge.

Pick one commit, several, or a range

Check out the branch that should receive the change, then name the commit:

git switch release
git cherry-pick 2d3f8f2

Find the hash with git log --oneline feature/a, or copy it from a graph. Several commits are applied in the order you list them, each as its own new commit:

git cherry-pick 2d3f8f2 0d810e7

For a run of consecutive commits, use a range. Watch the caret:

git cherry-pick A^..B    # A, B and everything between them
git cherry-pick A..B     # everything after A up to B: A itself is left out

A..B means “commits reachable from B but not from A”, so A is excluded. Forgetting the ^ is a common mistake. When we tried it, the second commit depended on the first, so leaving the first out made the pick stop on a conflict.

Useful options

  • -x adds a line to the new commit’s message saying where it came from: 
    a1

(cherry picked from commit 2d3f8f23457bf38dd0ef6169bcebcbb3911da3c6)
    This is handy on release branches, because anyone can trace the fix back to the original. It only makes sense when the original commit is pushed, so others can look it up.
  • --no-commit (or -n) applies the changes to your working tree and stages them, but makes no commit. Pick several commits this way and commit once, to get a single combined commit. It is also a way to look at the result before you commit it.
  • --edit (or -e) opens the editor so you can change the message before committing.

To undo a cherry-pick you have not pushed yet, remove the new commit with git reset --keep HEAD~1. If it is pushed, revert it instead. The undo guide explains the difference.

Cherry-picking a merge commit

A merge commit has two parents, so “what this commit changed” has two answers. Git refuses until you choose:

git cherry-pick c7a5063
error: commit c7a5063... is a merge but no -m option was given.
fatal: cherry-pick failed

-m 1 says “compare with the first parent”. The first parent is the branch that was merged into, usually main. So the result is everything the merged branch brought in, as one new commit:

git cherry-pick -m 1 c7a5063

-m 2 would compare with the second parent instead, which is rarely what you want. If you only need some of the commits from that branch, picking them one by one is often clearer than picking the merge.

Conflicts: continue, skip or abort

If the change does not apply cleanly, git stops and tells you which files conflict:

CONFLICT (content): Merge conflict in a.txt
error: could not apply 2d3f8f2... a1

The cherry-pick is now in progress. git status says so. You have three ways out:

  • Resolve and continue. Fix the files (VS Code lists them under Merge Changes in Source Control), git add them, then run git cherry-pick --continue. Git makes the commit and moves on to the next one, if you picked several.
  • Skip this commit with git cherry-pick --skip. Its changes are left out and git goes on with the next commit in the list.
  • Abort with git cherry-pick --abort. Your branch goes back to where it was before you started, including commits the same cherry-pick already made.

These work just like the rebase versions. The conflict guide covers resolving in VS Code in more detail.

In VS Code’s built-in graph

VS Code’s Source Control view has a graph of recent commits. In VS Code 1.147, right-clicking a commit there offers Cherry Pick. It applies that commit to your current branch. (We read this from the menus of the git extension bundled with VS Code 1.147; older versions may differ.) By default the graph follows your current branch, so to reach a commit on another branch you may first need to pick that branch in the graph’s branch picker (the branch filter guide describes it). If the pick conflicts, resolve the files in Source Control; the terminal commands above still apply. There is no option for -x, ranges or --no-commit, so use the terminal for those.

Do it in Mergeline

Mergeline is a free, MIT-licensed git graph for VS Code. It draws every branch, so the commit you want is on screen next to the branch it should go to.

  1. Right-click a commit on any branch and choose Cherry-pick onto “branch”, where branch is the branch you have checked out. If the commit is a merge, Mergeline asks which parent is the mainline (that is the -m number; parent 1 is usually right).
  2. Or drag it (new in 0.8). Drag a commit row onto the current branch’s badge, or onto the commit your branch points to (the HEAD row). A menu opens with Cherry-pick onto “branch”. Nothing runs until you choose it.
  3. If it stops on a conflict, a bar above the graph says a cherry-pick is in progress, which commit it stopped at and how many files conflict. Resolve and stage the files in Source Control, then press Continue. Skip leaves that commit out, and Abort puts the branch back. The bar also appears for a cherry-pick you started in a terminal.

Mergeline runs a plain git cherry-pick (with -m for merges), so it does not add -x. To pick a range, use the terminal command above; the new commits appear in the graph when it refreshes.
