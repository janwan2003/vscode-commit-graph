Find which commit changed a file or folder

“When did the auth code last change?” “Which commit deleted the setup doc?” “Who touched package.json on any branch?” All of these are searches of history by path, and git log answers them once you know how it reads paths. This guide covers paths, folders and patterns, searching every branch, the commits git hides by default, deleted files, and a path: search in VS Code. For the full history of one file, with renames and blame, see the file history guide.

We ran every command on this page with git 2.53 in a throwaway repository and quote the output we saw.

A file or a folder

git log --oneline -- src/auth
0e68aeb Auth: token refresh
1427501 Initial
git log -1 --format='%h %an %ad %s' --date=short -- src/auth
git log --oneline --stat -- src/auth           # which files, how many lines

Everything after -- is a path. A folder matches every file inside it, at any depth. You can list several paths, and exclude some with :!: git log -- src ':!src/auth'. Paths are relative to the directory you run git in; from inside src/, git log -- auth gave the same two commits. Start a path with :/ to make it relative to the top of the repository from anywhere.

A plain path matches from the start, not anywhere: git log -- auth run at the top found nothing, because there is no top-level auth. Matching is also case-sensitive, so src/AUTH found nothing either. The next section covers both.

Patterns: *.md, globs and case

git log --oneline --all -- '*.md'                # any .md file, any folder
git log --oneline --all -- ':(glob)*.md'         # .md files at the top level only
git log --oneline --all -- ':(glob)**/*.md'      # any folder again
git log --oneline --all -- ':(icase)*auth*'      # "auth" anywhere in the path, any case

Quote patterns so your shell does not expand them first. By default git’s * also matches /, so '*.md' found commits to README.md and to docs/setup.md: five commits in our test. With the :(glob) prefix, * stops at a slash and only ** crosses folders: ':(glob)*.md' found just the two commits that changed the top-level README.md. :(icase) ignores case, and the two combine as ':(glob,icase)**/login*'.

Every branch, and merges git hides

git log looks only at the current branch’s history unless you say otherwise. --all adds every branch, remote branch and tag. In our test, git log -- '*.md' on main found four commits; with --all it found a fifth, Docs on other branch, made on a branch that was never merged.

Git also simplifies history when you give a path. If a merge left the path exactly as one parent had it, git follows only that parent and skips the other side. We merged a branch that changed src/auth but kept main’s version of the files. The plain log showed two commits; --full-history showed four:

git log --oneline --full-history -- src/auth
b7b3f26 Merge feature (ours)
bcd7749 Feature tweak to login
0e68aeb Auth: token refresh
1427501 Initial

When a change you are sure was made does not show up, add --full-history before concluding it never happened.

Added or deleted files

git log --oneline -- docs/setup.md
5e56430 Remove setup doc
204f702 Docs: setup
git log --oneline --diff-filter=D --name-only -- docs
5e56430 Remove setup doc
docs/setup.md

For a file that no longer exists the -- is required: without it git stopped with fatal: ambiguous argument 'docs/setup.md': unknown revision or path not in the working tree. --diff-filter=D keeps only commits that deleted a matching file, and --name-only says which; use A for the commit that added it. If the file was renamed rather than deleted, --follow traces it back through its old name, for one file at a time.

By path and content

git log --oneline --all -S retryTimeout -- src/api
b4920a3 API: retry

-S finds commits that added or removed a string; with a path it searches only those files. -G takes a regular expression instead. Both are explained in the file history guide.

Search by path in Mergeline

Mergeline is a free, MIT-licensed git graph for VS Code. From version 0.11 its Find box searches by changed path as well as by subject, author, hash and branch name, and shows the matches in the graph, on their branches.

  1. Open Find with Ctrl+F (Cmd+F on macOS) in the graph.
  2. Type path: and some text, for example path:src/auth, path:package.json or path:*.md, and press Enter.
  3. Step through the matches with next and previous. Mergeline searches the whole history, not only the commits loaded so far, and loads a match’s place in the graph when you get to it.

Plain text matches any changed file or folder whose path contains it, ignoring case, much like ':(icase)*auth*' above. If the text has *, ? or [, it is used as a glob pattern instead.

What it does not do: it searches paths, not file contents, so use git log -S for that, and it steps through matches in the full graph rather than hiding the other commits. To narrow the graph to one file and follow it through renames, use Show File History in Mergeline from the file history guide. It also applies git’s default history simplification, the same as a plain git log -- <path>: a side branch whose change to the path was thrown away by its merge (for example -s ours) does not match. Run git log --full-history -- <path> in a terminal for those.

FAQ

How do I see what a found commit changed in that file?

git show <commit> -- <path> shows the diff for just that path, and git log -p -- <path> shows it for every match at once. In Mergeline, click the commit and then the file in its details.

Why does git log -- auth find nothing?

Plain paths match from the start of the path, relative to where you run git, so auth means a top-level auth file or folder. Write the full path, src/auth, or a pattern such as '*auth*'.

Which commit introduced a bug in this folder?

When you can test for the bug, git bisect is faster than reading the log: it checks out commits between a good and a bad one and asks you which is which. Passing a path, git bisect start <bad> <good> -- src/auth, limits it to commits that changed that folder.
