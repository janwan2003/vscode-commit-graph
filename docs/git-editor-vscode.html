Use VS Code as your git editor (commit messages and rebase -i)

When git needs text from you, such as a commit message, a tag message or the todo list of git rebase -i, it opens a file in its editor and waits for that program to exit. Out of the box that is usually Vim. This page shows how to make it VS Code instead, why the --wait flag matters, which setting wins when several are set, what to do when code is not found, the commands for VSCodium and Cursor, Windows quoting, and how to undo it. Commands were checked with git 2.53 and VS Code 1.147 on Linux.

Set VS Code as the editor

git config --global core.editor "code --wait"

From now on git opens a VS Code tab whenever it needs text: git commit without -m, git commit --amend, git tag -a without -m, a merge commit message, the git rebase -i todo list, and the messages for reword and squash lines. Type, save, and close the tab; git carries on when the tab closes. While it waits, git prints hint: Waiting for your editor to close the file... in the terminal.

Git runs the value through a shell and adds the file name at the end, so the command it runs is code --wait /path/to/repo/.git/COMMIT_EDITMSG. VS Code recognises that file, and git-rebase-todo, and highlights them with its built-in git commit and rebase syntax. Drop --global to set it for the current repository only.

This does not change VS Code’s own Source Control view, whose message box commits without an editor.

Why --wait is needed

Git treats the editor exiting as “I am done editing”. Plain code file hands the file to the VS Code window and exits at once, so git reads the file before you have typed anything. code --help describes the flag as Wait for the files to be closed before returning. We tested what git does with an editor that returns at once (the command true):

  • git commit stops with Aborting commit due to empty commit message.
  • git rebase -i runs the list as git wrote it, all pick, so nothing changes.
  • A reword keeps the old message.

Saving is not enough: git waits until the tab is closed. If you open the same file in two tabs, close both.

Only for rebase -i: sequence.editor

Git has a separate setting for the rebase -i todo list. Set it alone to edit the list in VS Code and keep your usual editor for commit messages:

git config --global sequence.editor "code --wait"                 # todo list only
GIT_SEQUENCE_EDITOR="code --wait" git rebase -i HEAD~3            # this once (bash, zsh)

The todo list and what each command in it does are explained in git rebase -i todo commands.

Which setting wins

Git picks the editor in this order and uses the first one that is set (from the git var documentation, and checked with git 2.53):

ForOrder
Commit and tag messages1. GIT_EDITOR environment variable
2. core.editor setting
3. VISUAL (skipped when TERM=dumb)
4. EDITOR
5. the default built into git, usually vi
The rebase -i todo list1. GIT_SEQUENCE_EDITOR environment variable
2. sequence.editor setting
3. whatever commit messages use (the list above)

A repository’s own core.editor (in .git/config) wins over your --global one, as with any git setting. The common surprise is a GIT_EDITOR variable set by your shell profile or by a tool: it beats core.editor, so your setting seems to be ignored. To see what git will actually run, and where a setting comes from:

git var GIT_EDITOR
git var GIT_SEQUENCE_EDITOR
git config --show-origin --get core.editor
file:/home/you/.gitconfig	code --wait

code: command not found

code --wait only works if code runs in a terminal. Check with code --version.

  • macOS: in VS Code, open the Command Palette (Cmd+Shift+P) and run Shell Command: Install ‘code’ command in PATH. Open a new terminal afterwards.
  • Windows: the installer adds VS Code to PATH unless you unticked that option. Open a new terminal after installing.
  • Linux: the .deb, .rpm and snap packages install code on the PATH.

Alternatively, give the full path. On macOS the command is inside the app; quote it because of the spaces (see below):

git config --global core.editor "'/Applications/Visual Studio Code.app/Contents/Resources/app/bin/code' --wait"

In the integrated terminal of a Remote-SSH, WSL or dev container window, VS Code provides its own code command that opens files in that window, so code --wait works there. In a terminal outside VS Code on the remote machine, it does not.

VS Code also has a setting, git.terminalGitEditor (off by default), that makes it the git editor for git commands run in its integrated terminal, without touching your git config. Restart the terminal after turning it on.

We tested code only; the other command names come from those editors. If yours is not found, look for that editor’s “Install command in PATH” command, as for VS Code above.

Windows and paths with spaces

In PowerShell and in Command Prompt, git config --global core.editor "code --wait" works as written. The Git for Windows installer can also set VS Code as git’s editor for you on its “default editor” page.

If you give a full path, remember that git runs the value through a shell (Git for Windows ships its own), which splits it at spaces. Put single quotes around the path inside the double quotes, and use forward slashes:

git config --global core.editor "'C:/Program Files/Microsoft VS Code/bin/code' --wait"

Without the inner quotes, git tries to run C:/Program and reports there was a problem with the editor. A per-user install lives under %LOCALAPPDATA%\Programs\Microsoft VS Code instead. Check what was stored with git config --global --get core.editor: it should print the single quotes. We checked this quoting rule with git’s shell on Linux, not on Windows itself.

Check it and undo it

git config --global --get core.editor        # what is set
git config --global --unset core.editor      # back to VISUAL, EDITOR or the default
git config --global --unset sequence.editor
git config unset --global core.editor        # the same in the newer syntax

If you set it in one repository without --global, run the --unset command there without --global. For a single command, git -c core.editor=vim commit overrides the setting without changing it.

No configuration: interactive rebase in Mergeline

Mergeline is a free, MIT-licensed git graph for VS Code. From version 0.21, its interactive rebase opens git’s todo list and commit messages in VS Code tabs without any of the setup above:

  1. Right-click the commit just below the oldest one you want to change, on the checked-out branch, and choose Interactive rebase of the commits after this…. Mergeline runs git rebase -i --autostash <that commit>.
  2. Edit the git-rebase-todo tab and press ✓ Start Rebase / Done in its title bar, or close the tab. ✕ Cancel Rebase makes git abort, so nothing changes. The bar above the graph shows the same choices while git waits.
  3. Messages for reword and squash lines open in a COMMIT_EDITMSG tab with Done and Abort rebase.
  4. Afterwards the notification offers Undo (git reset --keep to where the branch was).

Mergeline sets GIT_SEQUENCE_EDITOR and GIT_EDITOR for that one git process only, so it ignores and does not change your core.editor, and it does not need code on your PATH. That is why it also works in VSCodium, Cursor, Windsurf and remote or WSL windows. It covers rebases started from the graph; git commands you type in a terminal still use the editor you configured. Set mergeline.interactiveRebase to terminal to have Mergeline run git rebase -i in a terminal with your git editor instead. More in interactive rebase in VS Code.

FAQ

Git says “Aborting commit due to empty commit message” as soon as the tab opens.

The editor command has no --wait, so git saw it exit before you typed anything. Set it to code --wait.

The terminal says “Waiting for your editor to close the file” and nothing happens.

Git is waiting for the tab to close. Look for a COMMIT_EDITMSG or git-rebase-todo tab, possibly in another VS Code window, save it and close it.

I set core.editor but git still opens Vim.

Something with higher priority is set: a GIT_EDITOR variable, a repository-level core.editor, or, for rebase -i, sequence.editor or GIT_SEQUENCE_EDITOR. git var GIT_EDITOR and git config --show-origin --get core.editor show which.

Can I keep Vim for commit messages and use VS Code only for the todo list?

Yes: set only sequence.editor to code --wait. Messages for reword and squash lines still open in your commit editor.
