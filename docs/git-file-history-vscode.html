Git file history in VS Code: who changed this file, and when

Sooner or later you open a file and wonder how it got this way. Which commit added this function? Who changed the timeout last month? Git records the answer for every file, and you can get at it from VS Code in a few ways. This guide covers a file-history graph in Mergeline, the equivalent git commands, and VS Code’s own Timeline view.

See a file’s history in Mergeline

File history is new in Mergeline 0.2.0. It turns the commit graph into a graph of one file.

  1. Pick the file. Right-click it in the Explorer, on its editor tab, or anywhere inside the editor, and choose Show File History in Mergeline. You can also run Show File History in Mergeline from the Command Palette (Ctrl+Shift+P, or Cmd+Shift+P on macOS) for the file in the active editor.
  2. Read the graph. The graph now lists only the commits that touched that file. A banner at the top reads History of <path> with a commit count. The lanes stay connected: Mergeline asks git to rewrite each commit’s parents to the nearest earlier commit that also touched the file (the same thing git log --parents -- <path> does), so you still see which branch each change was made on and where it was merged.
  3. Inspect a change. Click a commit to open its details. The file you are tracking is highlighted in the list of changed files; click it to open the change in VS Code’s diff editor. The commit’s other files are listed too.
  4. Go back. Click Show all commits in the banner to return to the full graph.

Stashes and the uncommitted-changes row are hidden in this mode, because they cannot be filtered by path. The branch filter and the Remote branches checkbox still apply.

Renames are followed (since 0.3.0). If the file was renamed or moved, Mergeline finds its earlier names with git log --follow and keeps going; the bar above the graph shows them (“also as …”). A different file that later reused an old name is left out. Like --follow itself, this relies on git’s similarity guess, described below.

git log for one file

Every git log option works with a path. Put the path after --:

git log -- src/search.ts
git log --oneline --graph -- src/search.ts

The -- tells git that what follows is a path, not a branch name. You can sometimes leave it out, but it is required for a file that no longer exists in your working tree. A directory works as well as a file: git log -- src/ lists every commit that touched anything under src.

By default this shows the history of the current branch. Add --all to include every branch and tag, or name a branch: git log main -- src/search.ts.

--graph turns on what git calls parent rewriting: each commit shown is drawn as if its parent were the nearest earlier commit that touched the path, so the graph stays joined up instead of falling apart into dots. --parents does the same without drawing.

To see the changes themselves, add -p; the diff is limited to the paths you gave:

git log -p -- src/search.ts          # each commit with its diff, limited to this file
git log --stat -- src/search.ts      # line counts instead of the full diff

Following renames: --follow

git log --follow -- src/search.ts

Git does not store renames. It stores snapshots, and works out afterwards that a deleted file and an added file with similar content are probably the same file. A plain git log -- path looks only at that exact path, so it stops at the commit that created the file under its current name. --follow watches for that point, detects the rename, and carries on with the old name.

It only works for a single file. --follow tracks one path through history and swaps in the old name when it finds a rename, so it cannot track several paths at once: give it two and git stops with --follow requires exactly one pathspec. Renames are detected file by file, so point it at a file rather than a directory. Because rename detection is a similarity guess, a file that was renamed and heavily rewritten in the same commit may not be followed; doing the rename in a commit of its own avoids that.

Who changed this line: blame and pickaxe

git blame src/search.ts
git blame -L 40,60 src/search.ts      # only lines 40 to 60

git blame prints every line of the file with the commit, author and date that last changed it. Add -w to ignore whitespace-only changes, and -C to look through code that was moved or copied from other files. Keep in mind that blame shows the last change to a line: if someone reformatted the file, blame points at the reformat. Run git blame <commit>^ -- src/search.ts to look past that commit, or use the pickaxe.

git log -S'retryTimeout' -- src/search.ts
git log -G'retry(Timeout|Count)' -- src/search.ts

-S, the “pickaxe”, finds commits that changed the number of times a string appears in the file: the commit that added retryTimeout, and the one that removed it. A commit that only moved the string around does not count. -G takes a regular expression and matches any commit whose diff adds or removes a line containing it, so it also catches edits to lines that still contain the text. Both combine with -p.

To follow a function or a range of lines through history, git log -L 40,60:src/search.ts shows every commit that changed those lines, with the diff of just that range.

Seeing an old version of a file

git show 4e7d0c2:src/search.ts                  # the whole file as it was in that commit
git show 4e7d0c2:src/search.ts > /tmp/old.ts   # save it to compare
git restore --source=4e7d0c2 -- src/search.ts   # put that version back in your working tree

In <commit>:<path> the path is relative to the top of the repository, not your current directory. Start it with ./ to make it relative to where you are. The git restore line overwrites your copy of the file, so commit or stash any changes first.

VS Code’s built-in Timeline view

VS Code has its own per-file history, with nothing to install. Open a file, then expand Timeline at the bottom of the Explorer. It lists the git commits that changed the file, mixed with Local History entries that VS Code records when you save. Clicking an entry opens a diff against the previous version, and the filter button lets you hide either source.

It is quick, and Local History can save you when you never committed at all. It is a flat list, though: it does not show which branch a change was made on or where it was merged. Use the Timeline for a glance, and a graph when the branch structure matters.

FAQ

Why does the history skip merge commits?

That is git’s default history simplification. When you limit the log to a path, a merge commit is hidden if the file ended up identical to the file in one of its parents, because the merge itself did not change it, and git follows only that parent. You will see a merge only when it actually changed the file, for example while resolving a conflict. If a side branch changed the file but the merge discarded those changes, the side branch is pruned too. Add --full-history to see every commit that touched the path, including those, along with the merges that brought them in.

Can I see the history of a deleted file?

In a terminal, yes: git log --all -- path/to/old-file.ts. The -- matters here, since the path does not exist any more. Mergeline’s command needs a file you can right-click or open, so for a deleted file use the terminal.

Does it work in VSCodium, Cursor and Windsurf?

It is built for them (they install the same .vsix, and Mergeline uses only standard VS Code APIs); our automated tests run in VS Code 1.147. Download it from the latest GitHub release and run Extensions: Install from VSIX… (full steps). Listings on the VS Code Marketplace and Open VSX are coming soon.
