Add, rename, change URL and prune git remotes in VS Code

A remote is a name, such as origin, that stands for the URL of another copy of your repository. Most projects only ever have origin, until you fork something and need upstream, the repository moves to a new host, or the branch list fills up with branches that were deleted on the server months ago. This guide covers the git commands for each of those, what they do to your branches, what VS Code’s built-in Git offers, and Mergeline’s remote management.

We ran every command on this page with git 2.53 in throwaway repositories and quote the output we saw.

See your remotes

git remote -v
origin	git@github.com:you/app.git (fetch)
origin	git@github.com:you/app.git (push)

Each remote has a fetch URL and a push URL; they are the same unless you set them apart (see below). git remote get-url origin prints just the URL. git remote show origin contacts the remote and lists its branches, which local branches pull from and push to it, and which remote branches are stale: still in your repository but deleted on the server.

Each remote’s branches live in your repository as remote-tracking branches named <remote>/<branch>, like origin/main. They are your copy of where the remote’s branches were at your last fetch, and git branch -r lists them.

Add a remote

git remote add upstream https://github.com/project/app.git
git remote add -f upstream https://github.com/project/app.git   # and fetch it now

The usual reason is a fork: origin is your fork, upstream is the original project, and you fetch upstream to keep up with it. Plain git remote add only writes the configuration; no upstream/* branches exist until you run git fetch upstream. With -f, git fetches straight away and prints the new branches.

A name with a space, or one already in use, is refused (fatal: 'bad name' is not a valid remote name). After adding, git diff upstream/main...HEAD or git rebase upstream/main work like with any other branch.

Change a remote’s URL

git remote set-url origin git@github.com:you/app.git

Use this when the repository moved (renamed on the server, transferred to an organisation, migrated to another host) or when you switch between HTTPS and SSH. It only changes the address: your remote-tracking branches and every branch’s upstream stay as they are, because they refer to the remote by name. Run git fetch afterwards to check that the new address works.

To push somewhere other than where you fetch from, add --push: git remote set-url --push origin <url>. That stores a separate pushurl, and git remote -v then shows two different lines. Pointing set-url at a name that does not exist fails with error: No such remote 'name'.

Rename a remote

git remote rename origin old-origin

A rename does more than change a name. In our test, renaming origin to primary also:

  • renamed every remote-tracking branch, so origin/main became primary/main, including origin/HEAD;
  • updated the fetch refspec in the configuration to +refs/heads/*:refs/remotes/primary/*;
  • updated the upstream of each local branch that tracked it, so git status on feature then showed feature...primary/feature.

Renaming to a name that is already taken fails with error: remote fork already exists. A common use is moving to a fork: rename origin to upstream, then add your fork as the new origin.

Remove a remote

git remote remove upstream      # git remote rm does the same

This deletes the remote’s configuration and all its remote-tracking branches. Your local branches stay, including ones you created from that remote, but they lose their upstream: in our test, both branch.<name>.remote and branch.<name>.merge were deleted for a branch that tracked the removed remote, and git printed no warning. Plain git pull and git push on that branch then have nowhere to go until you set a new upstream with git push -u <remote> <branch> or git branch --set-upstream-to.

Nothing on the server is touched. Commits that only existed in that remote’s branches lose their names in your repository; you can add the remote again and fetch to get them back.

Prune deleted remote branches

When someone deletes a branch on the server, for example after merging a pull request, your origin/<branch> stays. A plain git fetch does not remove it. Over time git branch -r and every branch list fill up with branches that no longer exist. Pruning removes those stale remote-tracking branches:

git fetch --prune                      # fetch, then delete stale ones
From github.com:you/app
 - [deleted]         (none)     -> origin/old-feature
git remote prune --dry-run origin      # show what would go
git remote prune origin                # delete without fetching
git fetch --all --prune                # every remote

To prune on every fetch, set git config --global fetch.prune true, or remote.origin.prune true for one remote; we checked that both make a plain git fetch delete stale branches. Pruning with --prune left tags alone in our test, so a tag deleted on the server stays in your repository.

Pruning never deletes your local branches. A local branch whose upstream was pruned shows it in git branch -vv as [origin/old-feature: gone], and git status says Your branch is based on 'origin/old-feature', but the upstream is gone. That is a good signal that the branch was merged and you can delete it yourself.

What VS Code has built in

We read the commands and menus of the git extension bundled with VS Code 1.147 (its package.json and code). For remotes it offers:

  • Git: Add Remote… in the Command Palette, also in the … menu at the top of the Source Control view under Remote. It asks for the URL first (typed in, or picked from a provider such as GitHub when its extension is active), then for a name, which it checks for duplicates and invalid characters. It then runs git remote add and fetches the new remote right away.
  • Git: Remove Remote, in the same places. You pick a remote from a list and it is removed; the code we read shows no confirmation step.
  • Git: Fetch (Prune), also under Pull, Push in the same menu, and the git.pruneOnFetch setting (off by default) to prune on every fetch, including automatic fetches.
  • Git: Fetch From All Remotes and Git: Delete Remote Branch….

There is no command to rename a remote or change its URL, and no view that lists your remotes with their URLs. For those, use the terminal commands above.

Manage remotes in Mergeline

Mergeline is a free, MIT-licensed git graph for VS Code. Version 0.9 adds a list of your remotes with the everyday actions next to each one, so you do not need to remember the commands above.

  1. Open it with the Remotes… button in the graph’s toolbar, the command Mergeline: Manage Remotes, or by right-clicking a remote branch and choosing Manage remote “origin”… (with that branch’s remote name). The toolbar checkbox that shows or hides remote branches in the graph is now labelled Remote branches.
  2. See what you have. Each remote is listed with its URL.
  3. Add one. Choose Add remote…, enter a name and a URL, then choose whether to fetch it now.
  4. Act on a remote. Pick a remote for Fetch; Fetch and prune, which also removes remote-tracking branches whose branch was deleted on the remote; Change URL…; Rename…; Remove…, which asks before it removes anything; and Copy URL. When the URL is on GitHub, GitLab or Bitbucket, there is also Open on GitHub (or GitLab, or Bitbucket).

Renaming, removing and pruning change your remote-tracking branches exactly as described in the sections above, and the graph’s branch badges follow when it refreshes.

Mergeline is not on the VS Code Marketplace yet. Download the .vsix from GitHub and run Extensions: Install from VSIX… (full steps).
