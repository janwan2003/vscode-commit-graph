“Your branch is ahead of ‘origin/main’ by N commits”

git status compares your branch with the remote branch it tracks and tells you how far apart they are: ahead by the commits you have and the server does not, behind by the commits the server has and you do not, or diverged when both are true. This guide explains each message, why the numbers can be out of date, how to get the counts for one branch or all of them from the command line, and what to do with a branch whose upstream shows as [gone].

What ahead, behind and diverged mean

Most local branches have an upstream: the remote-tracking branch they were cloned from or first pushed to with -u, such as origin/main. git status counts the commits that are on one side and not the other, and picks one of four messages:

Your branch is up to date with 'origin/main'.

Your branch is ahead of 'origin/main' by 2 commits.
  (use "git push" to publish your local commits)

Your branch is behind 'origin/main' by 1 commit, and can be fast-forwarded.
  (use "git pull" to update your local branch)

Your branch and 'origin/main' have diverged,
and have 2 and 3 different commits each, respectively.
  (use "git pull" if you want to integrate the remote branch with yours)
  • Ahead by N: you made N commits that are not on the remote yet. Nothing is wrong; git push sends them.
  • Behind by N: the remote has N commits you have not taken. “Can be fast-forwarded” means you have nothing of your own on top, so pulling just moves your branch forward with no merge commit.
  • Diverged, N and M: both sides have new commits. The first number is yours (ahead), the second is theirs (behind). A plain push is refused until you combine them with a merge or a rebase.

The comparison is between two commits, not two sets of files. Two commits with identical content but different hashes, such as a commit you rebased after pushing it, still count on both sides.

The counts are as of your last fetch

git status never contacts the server. It compares your branch with your local copy of the remote branch, origin/main, which only moves when you run git fetch, git pull or git push. So the message can be stale. In our test, a colleague pushed three commits while we made two:

git status
Your branch is ahead of 'origin/main' by 2 commits.
git fetch
git status
Your branch and 'origin/main' have diverged,
and have 2 and 3 different commits each, respectively.

“Up to date with ‘origin/main’” therefore means “up to date with what I last fetched”. Fetch first whenever the answer matters. git fetch --all fetches every remote, not just the current branch’s.

Count it for one branch

git status -sb
## main...origin/main [ahead 2, behind 3]
git rev-list --left-right --count main...origin/main
2	3
git rev-list --left-right --count HEAD...@{upstream}   # the same, for whatever branch you are on

-s is the short status and -b adds the branch line; a branch that is in sync shows no brackets at all. rev-list prints two numbers separated by a tab: commits only on the left side of the three dots (yours, ahead) and only on the right (theirs, behind). The three dots matter: A...B means “on either side but not both”, and --left-right keeps the two sides apart. @{upstream}, or @{u} for short, means the current branch’s upstream, so you do not have to type its name.

To see the commits rather than count them, use two dots, which means “on the right, not on the left”:

git log --oneline @{u}..HEAD    # mine, not pushed
git log --oneline HEAD..@{u}    # theirs, not pulled

A branch without an upstream has nothing to compare with: git status -sb shows just ## local-only, and @{u} stops with fatal: no upstream configured for branch 'local-only'. Push it once with git push -u origin local-only, or point it at an existing remote branch with git branch -u origin/main.

Every branch at once

git for-each-ref --format='%(refname:short) %(upstream:track)' refs/heads
feature
main [ahead 2, behind 3]
old [gone]
git branch -vv
  feature e19df8f [origin/feature] f1
* main    a4255fe [origin/main: ahead 2, behind 3] Mine 2
  old     e19df8f [origin/old: gone] f1

%(upstream:track) is empty for a branch that is in sync or has no upstream; add %(upstream:short) to the format to tell the two apart. %(upstream:track,nobracket) drops the brackets, which is easier to parse in a script. git branch -vv is the readable version: the upstream in brackets, then the counts after a colon.

Both read local data, so they are only as fresh as your last git fetch, just like git status.

Getting back in sync

StatusUsual fix
Aheadgit push
Behindgit pull, or git merge --ff-only @{u} after a fetch, which refuses to make a merge commit
Divergedgit pull --rebase to replay your commits on top of theirs, or git pull --no-rebase to merge; see rebase vs merge. A plain git pull with neither set stops with fatal: Need to specify how to reconcile divergent branches.
Diverged because you rebased pushed commitsgit push --force-with-lease, only on a branch nobody else builds on
Behind, on a branch you are not ongit fetch origin main:main; see update a branch without checking it out

If you are ahead with commits you did not mean to make, for example on main instead of a feature branch, create a branch at the current commit with git branch my-work, then move main back to the remote with git reset --hard origin/main. The undo guide explains what --hard overwrites.

Upstream [gone]: branches deleted on the remote

When a pull request is merged, the hosting service usually deletes its branch on the server. Your local branch still points at origin/that-branch, which no longer exists. Git only notices when you prune. A plain git fetch left our deleted branch’s origin/old in place; --prune removed it:

git fetch --prune
 - [deleted]         (none)     -> origin/old
git branch -vv
  old     e19df8f [origin/old: gone] f1
git switch old && git status
Your branch is based on 'origin/old', but the upstream is gone.
  (use "git branch --unset-upstream" to fixup)

To prune on every fetch from now on, set git config --global fetch.prune true. Pruning only removes remote-tracking branches (origin/…); your local branches are never deleted by a fetch.

To list the local branches whose upstream is gone and delete them:

git for-each-ref --format='%(refname:short) %(upstream:track)' refs/heads | awk '$2 == "[gone]" {print $1}'
old
git branch -d old
error: the branch 'old' is not fully merged
hint: If you are sure you want to delete it, run 'git branch -D old'

-d refuses when the branch has commits that git cannot find in its upstream, or, once the upstream is gone, in your current branch. That is a real warning if you made commits after the pull request was merged. It is also common after a squash merge or rebase merge on the server, where your original commits never land on main under the same hashes. Check with git log --oneline main..old what would be lost, then use -D if you are sure. If you want to keep the branch and silence the message instead, git branch --unset-upstream old removes its upstream.

Ahead and behind in Mergeline

Mergeline is a free, MIT-licensed git graph for VS Code. From version 0.12 it shows the ahead and behind counts on the branch badges in the graph, for every branch at once, so you do not have to run git branch -vv.

  1. Read the badge. A local branch that tracks a remote branch shows ↑N for commits you have not pushed and ↓N for commits you have not pulled. A branch that is in sync shows neither.
  2. Hover it for the details, for example “Compared with origin/main as of the last fetch: 2 commits to push, 3 to pull”. Like git status, the counts come from your last fetch.
  3. Watch for ✕. It means the branch’s upstream was deleted on the remote, the same as [gone] above. Fetch and prune from the Remotes… button so Mergeline sees deletions; the remotes guide covers it.
  4. Act on it. Right-click the branch to push, pull, or delete it (Mergeline asks before force-deleting an unmerged branch). For a branch that is behind and not checked out, choose Update from origin/… (fast-forward), described in update a branch without checkout.

What it does not do: Mergeline does not fetch in the background, so the arrows do not change until you fetch. Branches with no upstream have no arrows.

FAQ

Git says “up to date”, but I know someone pushed. Why?

Because git status compares with your last fetch, not with the server. Run git fetch and check again.

I pulled, and now I am ahead by one commit. What is it?

A merge commit. When both sides had new commits, git pull --no-rebase (or a plain git pull with pull.rebase false configured) combines them with a merge commit, which exists only on your side until you push. git log --oneline @{u}..HEAD shows it.

Why is my branch ahead after git commit --amend or a rebase?

Rewriting a commit you already pushed gives it a new hash, so git counts your new version as ahead and the pushed version as behind: the branch has diverged. If you meant to replace the pushed commit, push with git push --force-with-lease; if others use the branch, do not rewrite it.

How do I compare with a branch other than the upstream?

Give both names: git rev-list --left-right --count feature...main counts commits only on feature and only on main. The compare branches guide shows the commits and files behind those numbers.
