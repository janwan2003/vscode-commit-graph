Rebase, merge or cherry-pick stopped with conflicts: continue, skip or abort

A rebase, merge, cherry-pick or revert that hits a conflict does not fail and go away. It stops halfway and waits for you, and until you finish or cancel it, the repository is in an in-between state. This guide shows how to tell which operation is waiting, how to resolve the files in VS Code, which command moves it on, and how to get back if the result is not what you wanted.

What is in progress?

git status says it in its first lines, together with the commands that apply:

git status
interactive rebase in progress; onto 0fd66d2
...
You are currently rebasing branch 'feature' on '0fd66d2'.
  (fix conflicts and then run "git rebase --continue")
...
	both modified:   f.txt

A plain git rebase also reports itself as “interactive rebase in progress”; that is just how the default rebase backend is labelled. Git keeps the state in files inside .git, which is how editors and tools (Mergeline included) detect it. In a linked worktree .git is a file, not a folder; git rev-parse --git-path rebase-merge prints the real location.

Resolve the conflicts in VS Code

Conflicted files appear in the Source Control view under Merge Changes. Open one and you see git’s conflict markers: your side between <<<<<<< and =======, the other side down to >>>>>>>. Above each block VS Code offers Accept Current Change, Accept Incoming Change and Accept Both Changes, or you can edit the text by hand. For a three-pane view, click Resolve in Merge Editor; the setting git.mergeEditor (off by default) opens conflicted files in it directly.

During a rebase the sides are the opposite of what you might expect. “Current” (HEAD) is the branch you are rebasing onto, and “incoming” is your own commit being replayed. The marker line >>>>>>> d8d10ab (Feature edits b) names that commit.

When a file looks right and has no markers left, stage it with the + button in Source Control or git add <file>. Staging is how git learns the conflict is resolved; saving the file is not enough. A file deleted on one side is resolved with git add (keep it) or git rm (delete it). The merge conflicts guide covers the markers, the merge editor and --ours/--theirs in more depth.

Continue, skip or abort

OperationContinueSkip this commitAbort
Rebasegit rebase --continuegit rebase --skipgit rebase --abort
Mergegit merge --continue or git commit(none)git merge --abort
Cherry-pickgit cherry-pick --continuegit cherry-pick --skipgit cherry-pick --abort
Revertgit revert --continuegit revert --skipgit revert --abort

Continue commits your resolution and moves to the next commit, if there is one. It refuses while any file is still unmerged (f.txt: needs merge). Skip leaves the current commit out entirely and moves on, so its changes are gone from the result. A merge is a single step, so it has nothing to skip. Abort puts the branch, the index and your files back as they were before the operation started. A rebase can stop several times, once for each commit that conflicts.

Why continue opens an editor, and how to avoid it

After a conflict, git assumes you may want to say something about the resolution, so it opens the commit message in your editor. git rebase --continue and git merge --continue always do this; cherry-pick --continue and revert --continue do it when run in a terminal. If the editor is Vim, type :wq to accept the message. To skip the editor and keep the message git prepared:

GIT_EDITOR=true git rebase --continue        # bash, zsh
git -c core.editor=true rebase --continue    # any shell

true is a command that does nothing and succeeds, so git takes the message unchanged. If a GIT_EDITOR variable is already set in your environment, it wins over core.editor and the second form has no effect. To get the message in a VS Code tab instead, see setting the editor.

“No changes” and empty commits

Sometimes the right resolution is to keep what is already there, so the commit being applied ends up changing nothing. What happens next depends on the command:

  • Rebase (the default backend, plain or -i) drops the now-empty commit and carries on; that is the default of its --empty=drop option.
  • Rebase with --apply, and git am, stop with No changes - did you forget to use 'git add'? If you did stage everything, run git rebase --skip.
  • Cherry-pick stops with The previous cherry-pick is now empty, possibly due to conflict resolution. Run git cherry-pick --skip to leave it out, or git commit --allow-empty to keep an empty commit as a record.
  • Revert stops with nothing to commit, working tree clean; the same two ways out apply, with git revert --skip.

Getting back after a bad finish

If you finished but resolved something wrongly, the old state is still there. A rebase and a merge both save the previous tip of your branch in ORIG_HEAD:

git reset --keep ORIG_HEAD

--keep refuses rather than overwrite uncommitted changes. A cherry-pick or revert does not set ORIG_HEAD; it adds one commit per picked commit, so git reset --keep HEAD~1 removes the last one. ORIG_HEAD is overwritten by the next reset, rebase or merge. After that, run git reflog: the entry just below rebase (start) is your branch before the rebase, and git reset --keep <that hash> puts it back. The undo guide covers the reflog and reset modes in more detail.

Do it in Mergeline

From Mergeline 0.7 the graph tells you when an operation is waiting, whether you started it from the graph or from a terminal.

  1. Read the bar. While a rebase, merge, cherry-pick or revert is in progress, a bar at the top of the graph says what it is and where it stopped, for example Rebasing main onto feature/x — step 2 of 4, stopped at 1a2b3c4 “Add export” · 2 conflicted files. Click the hash to select that commit in the graph.
  2. Resolve. Click Source Control in the bar to open the conflicted files, resolve them as described above, and stage them.
  3. Continue. Continue runs the matching --continue. It refuses while files are still unmerged (“resolve and stage them first”), asks again if a staged file still contains <<<<<<< conflict markers, and it never opens an editor: the commit message git prepared is kept. If the next commit conflicts too, the bar moves on to that step.
  4. Or skip or abort. Skip leaves out the commit that stopped (not shown for merges, which have no skip). Abort runs the matching --abort and puts everything back. Both ask first.

Edits made from the graph (editing a message, moving, squashing or dropping a commit) stop in this same bar if a commit conflicts. See also interactive rebase and rebase vs merge.
